# Agent Notes

## Header/footer navigation creates duplicate elements (huggingface.co/meta-llama/Llama-3.1-8B-Instruct)
Many sites (including HuggingFace) repeat navigation links in both the header and footer.
Before the fix, these appeared twice in the elements list (e.g. "Models", "Datasets",
"Spaces", "Pricing", "Docs", "Hugging Face" each collected 2×). Content links repeated in
the gated-model section (use-policy URL appearing twice) also caused duplicates.

Fix: in `processElement`, before collecting an `<a>` element, compute a dedup key of
`info.text + '\x00' + href`. If the key is already in `state.seenLinkKeys`, skip silently.
The `seenLinkKeys` Set is initialised in `getPageState()` on each extraction.
Key insight: only (same text, same href) pairs are deduplicated — links with the same href
but different text (e.g. HN time-link and comments link both at `item?id=X`) are intentionally
kept because they represent distinct affordances from the agent's perspective.

Capture script: `tmp/llama_capture.mjs` (reusable for similar HuggingFace model pages).
Tests added: `test_duplicate_same_text_same_href_link_collected_once` (test 55),
             `test_same_href_different_text_links_both_collected` (test 56).

## aria-hidden icon text contaminates innerText (cloud.google.com/products)
Material Icons on Google Cloud uses `<i class="google-material-icons" aria-hidden="true">arrow_forward</i>`
children inside links and buttons. Despite `aria-hidden`, `el.innerText` INCLUDES the icon ligature text
because `innerText` respects CSS visibility, not ARIA semantics.

Effects before fix:
- Links showed trailing icon tokens: "Get expert guidance ... services arrow_forward"
- Carousel nav buttons showed "arrow_back"/"arrow_forward" instead of their `aria-label`
  values ("Previous slide"/"Next slide")

Fix: Added `getAccessibleText(el)` helper in extractor.js (Helpers section). It starts with
`innerText || textContent`, then subtracts the text of all `[aria-hidden="true"]` descendants
using `split(hText).join('')` (handles multiple occurrences). Used in:
- `buildElementInfo` (main text field)
- `hasAccessibleLabel`
- `getAssociatedLabelText`
- `aria-labelledby` resolution in both functions
- peer-link text check in `processElement`

Bonus: icon-only buttons with `aria-label` now correctly show their aria-label as `text`
rather than the icon ligature token.

Capture script: `tmp/gcloud_capture.mjs` (gitignored, recreate as needed).
Test added: `test_aria_hidden_icon_text_stripped_from_element_label`

## <label> with no for-attr used as aria-labelledby target (google.com/maps)
Google Maps uses `<label id="ucc-N">Layers</label>` as the accessible name for a
`<button aria-labelledby="ucc-N">` — no `for` attribute, no wrapped control.
Before the fix the extractor collected this label as an interactive element (spurious
duplicate that does nothing when clicked; the button already resolves its text from
`aria-labelledby`).
Fix: in `processElement`, after the wrapped-control guard for LABEL, add:
```js
if (!el.hasAttribute('for')) { walkNode(el, depth, state); return; }
```
This preserves the existing `test_standalone_label_for_attribute_collected` test
(labels with `for` are still collected) while skipping id-only labels.
Capture script: `tmp/maps_capture.mjs` (gitignored; recreate as needed from `ted_capture.mjs`).

## Wrapping <label> hides inner form control (mail.google.com sign-in)
Google Sign-in uses `<label><input type="email">Email or phone</label>` (label wrapping input).
Before the fix, the extractor collected the `<label>` as an interactive element and never
recursed into it, so the `<input>` was silently dropped from the elements list.
Fix: in `processElement`, when a `<label>` element contains a non-hidden form control
(`input:not([type="hidden"]):not([aria-hidden="true"]), select, textarea`), recurse into it
instead of collecting the label itself. The associated label text is still captured via
`getAssociatedLabelText` in `buildElementInfo` when processing the inner `<input>`.
This pattern appears on any site using the label-wrapping-input accessibility pattern
(common in modern form libraries and Google's MDC components).

## Injecting extractor on CSP-protected pages (e.g. facebook.com)
Pages with strict CSP (like Facebook) block `page.addScriptTag()` with:
> Either the 'unsafe-inline' keyword, a hash, or a nonce is required.

`playwright_browser_evaluate` uses CDP internally and **bypasses CSP**. Use it to
inject the extractor code directly:
1. Call `playwright_browser_evaluate` with a function that sets up the chrome stub
   AND embeds the full extractor IIFE content, then calls `window.__msgHandler`:
```js
() => {
  window.chrome = { runtime: { onMessage: { addListener: function(fn) { window.__msgHandler = fn; } } } };
  (function () { /* full extractor.js IIFE content here */ })();
  var response;
  window.__msgHandler({ type: 'get_page_state' }, {}, function(r) { response = r; });
  return { elemCount: response.elements.length, elements: response.elements.map(...) };
}
```
Note: `playwright_browser_run_code` does NOT support `require` or `import` so you
cannot read files from Node.js context. Embed the code inline or use evaluate.
Also: `playwright_browser_run_code` filename param only allows `C:\Windows\...` paths.

## jest.spyOn on instance does not override prototype mock reliably
When `beforeEach` mocks `HTMLElement.prototype.getBoundingClientRect` via `jest.spyOn`, a
subsequent `jest.spyOn(specificElement, 'getBoundingClientRect')` inside a test does NOT
reliably shadow the prototype mock in all jest-jsdom versions. Use a direct function assignment
instead:
```js
specificEl.getBoundingClientRect = () => ({ width: 0, height: 0, ... });
```
This works because own-property methods always shadow prototype methods in JS without relying
on jest's spy machinery.

## <img> collected as interactive via cursor:pointer (github.com/anthropics/claude-code)
GitHub README badges use `<a href="camo.url"><img src="badge.png" alt=""></a>`. The `alt=""`
makes `hasAccessibleLabel` return false, so we walk into the anchor. The child `<img>` then has
`cursor:pointer` (inherited) and was being collected as an independent interactive element.
Fix: added `if (tag === 'IMG') return false;` at the top of `isInteractiveEl`.

## display:inline container with 0x0 rect hides children (github.com/anthropics/claude-code)
GitHub's repo header uses `<ul class="pagehead-actions" style="display:inline">` whose
`getBoundingClientRect()` reports `{width:0, height:0}` even though Fork/Star/Notifications
links inside are fully visible. The old `isContainerVisible` required `rect.width > 0 &&
rect.height > 0`, silently dropping the entire subtree.
Fix: `return style.display === 'inline' || (rect.width > 0 && rect.height > 0);`

## display:contents container with 0x0 rect hides children (github.com/anthropics/claude-code/issues)
GitHub's issues list page wraps issue rows inside a `<div style="display:contents">` whose
`getBoundingClientRect()` returns `{width:0, height:0}`. Elements with `display:contents`
generate no box of their own — their children are rendered directly by the parent — so
the browser reports a zero-size rect for the wrapper itself.
The old `isContainerVisible` check dropped this entire subtree (all 25 issue links missing).
Fix: `return style.display === 'inline' || style.display === 'contents' || (rect.width > 0 && rect.height > 0);`

## Image-only anchor link fix (github.com/explore)
GitHub Explore uses a card-layout pattern where each card has two `<a href>` elements pointing
to the same URL: a large image wrapper (no text, no aria-label) and a text heading link.
The extractor now filters out `<a href>` elements with no accessible label
(no text content, no `aria-label`, no `title`, and no child `<img alt>`).
Fix in: `browser-agent-core/content/extractor.js` — `hasAccessibleLabel()` + `processElement()`.

## <relative-time> collected instead of parent <a> (github.com/anthropics/claude-code/issues/42249)
GitHub issue date links use `<a href="...#issue-N"><relative-time ...>on Apr 1, 2026</relative-time></a>`.
In real browsers the parent `<a>`'s `innerText` is `""` (empty) because the `<relative-time>`
custom element defers its rendered text to JS. `textContent` on the `<a>` still contains
the static fallback text ("on Apr 1, 2026").
The `hasAccessibleLabel` function used `innerText` and found it empty → treated the `<a>` as
an image-only anchor → recursed into it → collected the cursor:pointer `<relative-time>` child
as a spurious independent interactive element, while the actual `<a>` link was silently dropped.
Fix: in `hasAccessibleLabel`, fall back to `textContent` when `innerText` is empty:
```js
var innerText = typeof el.innerText === 'string' ? el.innerText : '';
var rawText = innerText || el.textContent || '';
```
Key diagnostic: check `a.innerText` vs `a.textContent` when an anchor wrapping a custom element
is missing from the extractor output. Also verify by running `playwright_browser_evaluate` with
a self-contained extractor snippet (see note above).

## aria-labelledby not resolved for icon buttons (docs.github.com/en/actions)
Many modern UI libraries (GitHub Docs, Primer CSS) use `aria-labelledby` pointing to tooltip
elements for icon buttons (language picker, hamburger menu). The extractor previously showed
these as buttons with empty text, making them unidentifiable to agents.
Fix: In `buildElementInfo`, after computing `text` from innerText/textContent, if `text` is
still empty and `aria-labelledby` is present, resolve each referenced element ID via
`document.getElementById` and join their text content. Also added `aria-labelledby` to
`COLLECT_ATTRS`. Added 2 tests: `test_aria_labelledby_resolved_in_text` and
`test_aria_labelledby_multiple_ids_resolved`.

## buildElementInfo text shows as "" for <relative-time>-wrapped anchors (github.com/axios/axios/issues/6973)
Even after the hasAccessibleLabel fix above, `buildElementInfo` still had a different bug:
```js
// BUGGY: when innerText==="" (empty string), ternary returns "", then "" || "" = ""
var rawText = (typeof el.innerText === 'string' ? el.innerText : el.textContent) || '';
```
This caused the `text` field to be `""` for all ~11 date links on the page even though they
were correctly collected. Agents could not distinguish them.
Fix: apply the same `innerText || textContent` pattern in `buildElementInfo`:
```js
var _innerText = typeof el.innerText === 'string' ? el.innerText : '';
var rawText = _innerText || el.textContent || '';
```
Diagnosis tip: if collected elements have `text: ""` but ARE in the list, check `buildElementInfo`
not `hasAccessibleLabel`. Run the extractor in the live browser via `playwright_browser_evaluate`
and inspect the `text` field of the returned JSON.

## Empty-alt img before non-empty-alt img causes anchor to be missed (en.wikipedia.org/wiki/Artificial_intelligence)
Wikipedia's logo uses: `<a href="/wiki/Main_Page"><img alt="" aria-hidden="true"><span><img alt="Wikipedia"></span></a>`.
The `querySelector('img[alt]')` selector matches ANY img with an alt attribute, including `alt=""`.
When the first img has `alt=""`, `img.getAttribute('alt')` returns `""` (falsy), causing:
- `hasAccessibleLabel(a)` returns false → anchor skipped, extractor recurses into children
- Child `<span>` with cursor:pointer gets collected as spurious element instead of the anchor
Fix: use `img[alt]:not([alt=""])` in both `hasAccessibleLabel` and `buildElementInfo` to skip
empty-alt images. This was applied to both places where `querySelector('img[alt]')` was used.
Test: `test_anchor_with_empty_alt_first_img_then_nonempty_alt_img_collected` (test 31).

## <input type="submit"> text was empty (news.ycombinator.com)
HN's comment form uses `<input type="submit" value="add comment">`. DOM textContent/innerText
for submit/button/reset inputs is always empty — the label is in `value=`. Added fallback in
`buildElementInfo` after the img-src fallback:
```js
if (!text && el.tagName === 'INPUT') {
  var inputType = (el.getAttribute('type') || '').toLowerCase();
  if (inputType === 'submit' || inputType === 'button' || inputType === 'reset') {
    var inputValue = el.getAttribute('value');
    if (inputValue) text = inputValue.replace(/\s+/g, ' ').trim().slice(0, 80);
  }
}
```
Tests: `test_input_submit_text_uses_value_attribute` (test 32) and related tests 33-35.

## cursor:pointer wrapper hides <select> inside (instagram.com)
Instagram's language selector uses a `<span style="cursor:pointer">` wrapping a
`<select aria-label="Switch Display Language">`. Before the fix, the extractor
captured the outer span (cursor:pointer + accessible label) and stopped recursion,
so the `<select>` was never visited.

Fix: Added `hasSemanticInteractiveDescendant(el)` helper. When a cursor-only
interactive element (non-semantic, cursor:pointer) has semantic interactive
descendants (button/a/input/select/ARIA-role elements), skip collecting the
wrapper and recurse instead to surface the semantic children.

The select has `opacity: 0` (transparent, overlaid by custom UI) but
`display: block`, `visibility: visible`, `pointer-events: auto` — so it IS
interactable even though invisible. The extractor's `isVisible()` does NOT check
`opacity`, which is correct for these cases.

Pattern to watch for: any SPA that renders a custom-styled dropdown/selector
on top of a native `<select>` (accessibility shim) can trigger this issue.

## CSS-override closed <details> hides dropdown content (workspace.google.com/products/drive/)
Some sites (e.g. Google Workspace) use `<details>` as a semantic container for CSS-driven
dropdowns. They override the UA `display:none` for non-summary children, so the dropdown
content is actually visible in the browser even though the `<details>` lacks `open` attribute.
The old extractor applied a hard-coded "if no `open` attr → only process `<summary>`" rule,
causing all navigation dropdown links (Solutions/Products/Industries/Resources) to be dropped.

Fix: removed the `open`-attribute-based shortcut entirely. The extractor now relies on the
actual computed CSS (`display`, `visibility`, `getBoundingClientRect`) for every element.
Real browser behaviour is preserved:
- Standard closed `<details>`: UA stylesheet sets non-summary children to `display:none` →
  correctly skipped.
- CSS-override closed `<details>`: non-summary children have `display:block` and non-zero
  rect → correctly collected.

Test update required: jsdom does not apply UA stylesheet, so tests for closed `<details>` must
wrap non-summary content in `<div style="display:none">` to simulate real browser behaviour.

Capture script: `tmp/drive_capture.mjs` (reusable). Element count: 168 → 219 after fix.

## One-dimensional zero-size wrapper can hide visible children on YouTube channel shelves
YouTube uses structural wrappers whose own `getBoundingClientRect()` collapses in
ONE dimension while visible controls overflow out of the wrapper:
- shelf arrows live inside wrappers with `width: 0; height: >0`
- per-card overflow menus (`button[aria-label="Action menu"]`) live inside wrappers with `height: 0; width: >0`

The old `isContainerVisible()` only allowed normal positive-size boxes (plus
`display:inline` / `display:contents`, and one old `height:0` special case), so
these wrappers could block traversal and hide real buttons.

Fix: treat containers with exactly one collapsed dimension as traversable when
`overflow`, `overflowX`, or `overflowY` is `visible`.

Related subtlety: if a cursor:pointer custom wrapper is itself considered
interactive, `processElement()` can return early on `!isVisible(el)` BEFORE it
recurses into visible semantic descendants. For YouTube's zero-height `#menu`
wrapper this hid the real `Action menu` button. Recurse through non-semantic
interactive wrappers before the final `isVisible()` gate.

## input[type=range] with pointer-events:none dropped (amazon.com/s?k=laptop)
Amazon's price-range filter uses `<input type="range">` elements with `pointer-events: none` so
that custom overlay drag handlers (divs positioned above the range inputs) can intercept mouse
events and update the inputs programmatically. The inputs themselves are still aria-labelled
(`aria-label="Minimum price"`, `aria-valuetext="$2"`) and keyboard-accessible.

The old `isVisible()` function checked `style.pointerEvents === 'none'` and returned false for
ANY element, which correctly excluded non-interactive divs/spans but incorrectly dropped these
semanticly-interactive range inputs.

Fix: in `isVisible()`, skip the pointer-events check for native form controls (INPUT, SELECT,
TEXTAREA). These can legitimately have `pointer-events:none` as a CSS override technique while
remaining fully usable via keyboard (arrow keys for range sliders, tab focus, etc.).

Note: Amazon's checkbox filters use `<input type="checkbox" aria-hidden="true">` decorative
inputs that are correctly skipped by `shouldSkip()` (aria-hidden check). The actual filter
interaction uses `<a href>` links — no bug there.

Test: `test_input_range_with_pointer_events_none_is_collected` (test 51 in extractor.test.js).

## aria-labelledby pointing to image-only element gives empty text (amazon.com/dp/B0947BJ67M)
Amazon product pages use `<input type="submit" role="radio" aria-labelledby="a-autoid-N-announce">`
for product image thumbnail navigation. The announce element contains only `<img alt="" src="thumbnail.jpg">`
(empty alt = decorative image per HTML spec), so `innerText`/`textContent` of the announce
element is always empty. Previous `aria-labelledby` resolution returned empty string, leaving
these thumbnail buttons with no label — completely unidentifiable to agents.

Fix: in `buildElementInfo`, when `aria-labelledby` resolution yields empty text, also check if
the referenced element contains `img[alt]:not([alt=""])` (use alt text) or `img[src]` (use
src filename as `[img: filename.jpg]`). Same fallback mirrored in `hasAccessibleLabel` so that
native `<button aria-labelledby="img-only-div">` elements are NOT dropped by the unlabeled-button
guard (which checks `hasAccessibleLabel` before deciding whether to collect or skip a button).

Also added `cursor: zoom-in` and `cursor: zoom-out` to `INTERACTIVE_CURSORS` (image zoom
overlays use these cursors).

Capture script: `tmp/amazon_capture.mjs` (reusable for similar Amazon product pages).
Test added: `test_aria_labelledby_img_only_element_uses_src_filename` (test 52 in extractor.test.js).

## sr-only inputs collected due to 1x1 bounding-rect (huggingface.co/models)
Modern Tailwind v3+ sr-only class uses `clip-path: inset(50%)` (not the old `clip: rect(0,0,0,0)`)
to visually hide elements from sighted users. These elements report a 1x1 bounding-rect which
passes the extractor's `rect.width > 0 && rect.height > 0` visibility check, causing them to
appear as interactive elements.

On HuggingFace's models page, the parameter-range filter uses two `<input type="range" class="sr-only">`
elements for the range slider. Both were incorrectly collected with identical confusing text
(all tick labels concatenated from the parent label), making them indistinguishable.

Fix: in `isVisible()`, when `rect.width <= 1 && rect.height <= 1`, additionally reject the
element if `style.clip !== 'auto'` (old pattern) OR `style.clipPath !== 'none'` (modern pattern).
This does not affect the Amazon range-slider fix (pointer-events:none native form controls)
because those have normal non-1x1 bounding-rects.

Capture script: `tmp/hf_capture.mjs` (reusable for HuggingFace pages).
Test added: `test_sr_only_input_not_collected` (test 53 in extractor.test.js).
