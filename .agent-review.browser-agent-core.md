# Review: `browser-agent-ext/lib/browser-agent-core`

Date: 2026-04-19

## Scope / method
- Static review of `background/`, `content/`, and `tests/`
- Cross-check of existing unit/integration coverage
- Attempted test execution, but `npm test` could not be run successfully in the current workspace because the Windows Node/npm setup resolved the UNC working directory incorrectly (`CMD.EXE ... UNC paths are not supported`), so findings below are from code review plus test inspection

## Critical
- No critical issues found.

## High

### 1. `BrowserBridge.getPageState()` hard-codes the extractor asset path and treats every first messaging failure as “content script missing” ✅
**Refs:** `browser-agent-ext/lib/browser-agent-core/background/browser-bridge.js:30-63`, `browser-agent-ext/lib/browser-agent-core/content/extractor.js:371-397`

`getPageState()` retries by injecting `lib/browser-agent-core/content/extractor.js` whenever the first `sendMessage` attempt fails. That has two concrete problems:

1. The injected file path is tied to one specific extension bundle layout, even though this package is presented as a reusable core library.
2. The catch block swallows the original failure reason and assumes reinjection is the right fix for timeouts, restricted pages, permission errors, and other runtime failures.

Impact:
- embedders with a different build/output layout will fail at runtime
- restricted pages or transient messaging failures get misdiagnosed as missing content scripts
- the Chrome-extension boundary becomes flaky and hard to debug

Recommendation:
- make the extractor path/config injectable instead of hard-coded
- distinguish “receiving end does not exist” from timeout/permission/runtime failures
- add dedicated `BrowserBridge` tests for restricted tabs, timeouts, and alternate packaging layouts

### 2. `verifyDone` fails open, so verification outages can incorrectly mark unfinished tasks as complete ✅
**Refs:** `browser-agent-ext/lib/browser-agent-core/background/agent.js:429-510`

When `verifyDone` is enabled, `_verifyDone()` still returns `{ verified: true }` if:
- the verification LLM call throws (`catch` at lines 485-488), or
- the verifier response cannot be parsed (`catch` at lines 507-509)

That means a provider outage, rate limit, network issue, or schema drift turns the safety check into an automatic success path.

Impact:
- users can receive false-success results exactly when they opted into stricter completion checks
- incomplete submissions/forms can be reported as done with no recovery path

Recommendation:
- fail closed by default (or make the policy configurable)
- surface a retriable error / continue the task instead of silently accepting completion
- add tests for verification fetch failures and unparsable verification payloads

## Medium

### 3. Loop-detection state leaks across separate `run()` calls ✅
**Refs:** `browser-agent-ext/lib/browser-agent-core/background/agent.js:41-47`, `browser-agent-ext/lib/browser-agent-core/background/agent.js:79-88`, `browser-agent-ext/lib/browser-agent-core/background/agent.js:396-415`, `browser-agent-ext/lib/browser-agent-core/tests/background/agent.test.js:387-401`

`AgentCore` initializes `_recentActions` in the constructor, but `run()` resets `_history`, `_sessionId`, and `_turnCounter` without clearing `_recentActions`.

So a new task inherits the previous task’s recent action history. If the new task starts on the same URL and repeats the same first action, the second step of the new run can be incorrectly tagged as a loop even though it is the first repetition in that run.

Impact:
- prompt pollution between unrelated tasks
- false “LOOP DETECTED” warnings that steer the LLM away from the correct action

Test gap:
- `test_loop_resets_on_new_run` only checks the first prompt of the second run, so it misses the leaked warning that would appear on the next iteration

Recommendation:
- reset `_recentActions` at the start of every `run()`
- add a regression test that performs at least one real action in run #2 before asserting no loop warning

### 4. Typing verification treats “could not read the field” as success, which can hide real input failures ✅
**Refs:** `browser-agent-ext/lib/browser-agent-core/background/executor.js:98-117`, `browser-agent-ext/lib/browser-agent-core/background/executor.js:129-170`, `browser-agent-ext/lib/browser-agent-core/background/browser-bridge.js:144-152`, `browser-agent-ext/lib/browser-agent-core/content/extractor.js:26-29`, `browser-agent-ext/lib/browser-agent-core/content/extractor.js:336-350`, `browser-agent-ext/lib/browser-agent-core/content/extractor.js:382-395`

`_typeSucceeded()` returns `true` when the read-back value is `null`. In practice, `null` can mean much more than “rich-text editor is unreadable”:
- `get_element_value` timed out
- the content script was reloaded/reinjected
- `indexToElement` is stale after a rerender
- the element disappeared before verification

Those cases are currently counted as successful typing.

Impact:
- silent false positives after typing
- the agent records `Executed type: ...` even when it never confirmed the text landed in the intended field
- later failures are harder for the LLM to attribute to the real cause

Recommendation:
- distinguish “unreadable but present” from “lookup failed / timed out / stale map”
- consider requiring at least one positive confirmation path before declaring success
- add tests for stale `indexToElement`, reinjection, and `getElementValue()` timeout behavior

### 5. Action validation only protects index-based actions; malformed `wait`/`scroll`/`navigate` payloads slip through ✅
**Refs:** `browser-agent-ext/lib/browser-agent-core/background/agent.js:355-390`, `browser-agent-ext/lib/browser-agent-core/background/executor.js:28-47`

`_validateAction()` only validates the structure of the action object itself plus indices for `click`, `type`, `select_option`, and `scroll_element`. Other actions are not schema-checked.

Examples:
- `{"action":{"wait":{}}}` reaches `_sleep(params.seconds * 1000)`, producing `NaN`
- `{"action":{"navigate":{}}}` reaches `chrome.tabs.update(..., { url: undefined })`
- invalid `scroll.direction` / `scroll.amount` values silently degrade to fallback behavior instead of generating a clean corrective retry

Impact:
- malformed LLM outputs are handled late and inconsistently
- some invalid payloads fail deep in Chrome APIs; others fail silently
- recovery becomes harder than it needs to be

Recommendation:
- add per-action schema validation before execution
- keep executor failures for environmental/runtime issues, not basic shape errors
- add unit tests for malformed non-index actions

### 6. The only integration-style test is both stale and excluded from Jest ✅
**Refs:** `browser-agent-ext/lib/browser-agent-core/jest.config.js:1-5`, `browser-agent-ext/lib/browser-agent-core/tests/integration.js:235-372`

`jest.config.js` only runs `**/tests/**/*.test.js`, so `tests/integration.js` never executes in the normal test run. On top of that, the file still targets the old API:
- `fakeAgent.buildUserMessage(...)` (current class exposes `_assembleUserMessage` instead)
- top-level `done` / `actions[]`
- executor mock expecting arrays instead of a single action object

Impact:
- there is no current end-to-end guard for the v2 agent/message/executor contract
- the repository carries a misleading integration test that no longer reflects production behavior

Recommendation:
- either rewrite this file to the current v2 API and include it in CI, or remove it to avoid false confidence
- add explicit `BrowserBridge` coverage, since the Chrome boundary is currently the least-tested part of the core

## Low


### 7. The bridge/executor contract is implicit; tests rely on capabilities that `BrowserBridge` does not define ✅
**Refs:** `browser-agent-ext/lib/browser-agent-core/background/executor.js:81-86`, `browser-agent-ext/lib/browser-agent-core/background/executor.js:289-323`, `browser-agent-ext/lib/browser-agent-core/background/browser-bridge.js:15-163`, `browser-agent-ext/lib/browser-agent-core/tests/background/executor.test.js:33-41`

`ActionExecutor` conditionally uses `focusElement`, `scrollElementIntoView`, and `scrollToPosition`, but `BrowserBridge` does not implement or document these methods. The tests mock them as if they are part of the standard bridge contract.

Impact:
- embedders can follow the documented `BrowserBridge + ActionExecutor` composition and still miss behavior the executor is designed to take advantage of
- the extension boundary is harder to reason about because the actual required interface lives partly in tests and optional `typeof fn === 'function'` checks

Recommendation:
- formalize a real bridge/capabilities interface
- either implement/document these helpers on `BrowserBridge` or inject a distinct DOM-assistance adapter
- add focused tests around whichever contract becomes official

## Residual risk
- The main unresolved risk is the Chrome-extension seam (`BrowserBridge` + content script messaging). That is where the code is most stateful, least covered by tests, and most dependent on packaging/runtime assumptions.
