## High

### 1. `armTab()` can resurrect observability after a disconnect/release race ✅
**Files:**
- `browser-agent-ext/lib/pi-browser-agent-bridge/src/buffers/console-buffer.js` (`ConsoleBufferManager.armTab`, `disconnectTab`, `releaseTab`)
- `browser-agent-ext/lib/pi-browser-agent-bridge/src/buffers/network-buffer.js` (`NetworkBufferManager.armTab`, `disconnectTab`, `releaseTab`)

**Why this matters**
Both buffer managers allow an `armTab()` call to stay in flight while `disconnectTab()` or `releaseTab()` runs. There is no cancellation token / generation check around the awaited attach path.

The sequence is:
1. `armTab(tabId)` starts and awaits `inspector.acquire()` / `ensureAttached()`.
2. Before that await resolves, `disconnectTab(tabId)` or `releaseTab(tabId)` runs and clears current subscriptions/lease.
3. The original `armTab()` continuation resumes later and still:
   - registers subscriptions,
   - stores a lease,
   - sets `state.armed = true`.

**Impact**
- leaked CDP lease
- leaked event subscriptions
- detached/removed tabs can become re-armed unexpectedly
- observability state can become internally inconsistent after tab removal or debugger detach

This is a real lifecycle bug, not just a theoretical concern; the code path has no guard after the awaited attach completes.

**Recommendation**
Add a per-tab arm generation or abort token and verify it after each `await` inside `armTab()`. If the tab was disconnected/released while arming, tear down the lease immediately and do not install subscriptions.

**Test gap**
No test currently covers `disconnectTab()`/`releaseTab()` racing with an in-flight `armTab()`.

### 2. Service-worker restart handling does not actually restore live observability ✅
**Files:**
- `browser-agent-ext/lib/pi-browser-agent-bridge/README.md`
- `browser-agent-ext/lib/pi-browser-agent-bridge/src/buffers/lifecycle.js` (`armExistingTabs`)
- `browser-agent-ext/background/pi-bridge-runtime.js` (`warmUp`, `setEnabled`)

**Why this matters**
The README says the bridge should keep console/network observability alive across service-worker restarts. The library even exposes `createObservabilityLifecycle().armExistingTabs()` for that purpose.

But the runtime warm-up path only does:
- attach event hooks
- mark itself warmed

It never calls `armExistingTabs()` on startup or re-enable.

**Impact**
After a service-worker restart (or disable → enable), persisted snapshots may still exist, but **live CDP subscriptions are not restored** until some later request happens to arm a tab again. Any console/network activity during that gap is silently lost.

**Recommendation**
Call `observability.armExistingTabs()` during warm-up / enable, and add an integration test that simulates worker restart and verifies capture resumes without waiting for another tool request.

## Medium

### 3. Buffer persistence silently ignores `chrome.runtime.lastError` ✅
**Files:**
- `browser-agent-ext/lib/pi-browser-agent-bridge/src/buffers/console-buffer.js` (`hydrateTab`, `persistTab`)
- `browser-agent-ext/lib/pi-browser-agent-bridge/src/buffers/network-buffer.js` (`hydrateTab`, `persistTab`)
- Contrast: `browser-agent-ext/lib/pi-browser-agent-bridge/src/config.js` (`readPiBridgeConfig`)

**Why this matters**
The buffer managers wrap `storageArea.get()` / `storageArea.set()` in promises, but those wrappers never inspect `chrome.runtime.lastError`. In Chrome extension APIs, callback invocation does **not** imply success.

So quota errors, backend failures, or storage access failures will be treated as:
- a successful write, or
- an empty read.

**Impact**
Observability data can be dropped silently, and callers/logs will think persistence succeeded.

**Recommendation**
Use a shared storage helper that rejects when `chrome.runtime.lastError` is set, similar to `readPiBridgeConfig()`.

**Test gap**
There are tests for config read failures, but none for console/network buffer storage failures.

### 4. Removed-tab snapshots are never cleaned up from memory or storage ✅
**Files:**
- `browser-agent-ext/lib/pi-browser-agent-bridge/src/buffers/lifecycle.js` (`handleTabRemoved`)
- `browser-agent-ext/lib/pi-browser-agent-bridge/src/buffers/console-buffer.js` (`releaseTab`, `dispose`)
- `browser-agent-ext/lib/pi-browser-agent-bridge/src/buffers/network-buffer.js` (`releaseTab`, `dispose`)

**Why this matters**
On tab removal, the lifecycle does:
- `disconnectTab()`
- `persistTab()`
- `releaseTab()`

But it never:
- removes the in-memory `_states` entry, or
- removes the persisted storage key (`piBridge.consoleBuf.*` / `piBridge.networkBuf.*`).

There also does not appear to be any later cleanup path for those persisted snapshots.

**Impact**
Closed-tab data accumulates indefinitely:
- memory retention during long-lived worker sessions
- growing `chrome.storage.local` usage
- eventual quota pressure

This looks especially wasteful because closed-tab snapshots are not easily reachable through the current request flow.

**Recommendation**
Add an explicit tab-eviction path that persists a final snapshot if needed, then removes both the in-memory state and the storage entry.

### 5. In-flight network requests are lost on suspend/disconnect/restart ✅
**Files:**
- `browser-agent-ext/lib/pi-browser-agent-bridge/src/buffers/network-buffer.js` (`createTabState`, `persistTab`, `disconnectTab`, `flushAll`)

**Why this matters**
`NetworkBufferManager` only persists completed `entries`. Requests that are currently in `state.inFlight` are never serialized, and they are not finalized as interrupted/failed during suspend or disconnect.

**Impact**
If the MV3 worker suspends, the debugger detaches, or the bridge restarts while requests are active, those requests disappear entirely from the restored history. That leaves a blind spot exactly around unstable/restart scenarios where observability is most valuable.

**Recommendation**
Either:
- persist `inFlight` requests as partial entries, or
- finalize them during disconnect/suspend with an explicit interrupted status/reason.

**Test gap**
Current persistence tests only cover completed requests.

### 6. Default `settle` / `networkidle` fallback does not actually wait beyond `status === "complete"` ✅
**File:**
- `browser-agent-ext/lib/pi-browser-agent-bridge/src/handlers/js-navigation-family.js` (`waitForTabSettled`, `waitForNavigationAfterAction`)

**Why this matters**
Without custom runtime hooks, the fallback implementation for `wait_until: "settle"` / `"networkidle"` is effectively the same as `"load"`:
- `waitForNavigationAfterAction()` resolves when `tabs.onUpdated(... status: 'complete')` fires
- then it calls `waitForTabSettled(..., skipImmediateComplete: false)`
- the fallback sees the tab is already complete and returns immediately

So there is no extra settle/network-idle behavior in the default implementation.

**Impact**
The handler API advertises stronger waiting semantics than the fallback actually provides. That makes the module easy to reuse incorrectly outside the extension runtime, and it hides a behavior difference between tests/reuse and production integration.

**Recommendation**
Either implement real settle/network-idle behavior in the fallback, or reject those modes unless a custom waiter is provided.

## Low

### 7. Response-body timeout helper leaves timers alive until timeout even after success ✅
**File:**
- `browser-agent-ext/lib/pi-browser-agent-bridge/src/buffers/network-buffer.js` (`withTimeout`)

**Why this matters**
`withTimeout()` creates a timeout for `Network.getResponseBody`, but never clears it when the body fetch succeeds early.

**Impact**
Usually minor, but in a service-worker environment unnecessary pending timers can:
- keep work alive longer than needed
- create avoidable timer churn when many response bodies are fetched

**Recommendation**
Track the timer handle and clear it in a `finally` block.

### 8. Package boundary is weak: consumers rely on deep imports into `src/` ✅
**Files:**
- `browser-agent-ext/lib/pi-browser-agent-bridge/package.json`
- `browser-agent-ext/background/sw.js`
- `browser-agent-ext/background/pi-bridge-runtime.js`

**Why this matters**
The package export surface only exposes `"." -> "./src/index.js"`, but real consumers import deep internal modules such as:
- `src/dispatcher.js`
- `src/buffers/lifecycle.js`
- `src/handlers/...`

That means the internal file layout is already a de facto public API.

**Impact**
Refactoring the library internals becomes much riskier than the package manifest suggests.

**Recommendation**
Either:
- export supported submodules explicitly, or
- move composition/wiring behind stable root exports.

---

## Overall assessment
The package is in decent shape at the unit level, and the existing tests catch many happy-path and error-normalization scenarios. The biggest remaining risks are around **lifecycle races**, **service-worker restart behavior**, and **persistence reliability under failure conditions**.

If I were prioritizing fixes, I would do them in this order:
1. Fix the `armTab()` race.
2. Restore observability on warm-up / re-enable.
3. Make storage failures visible.
4. Clean up removed-tab state.
5. Decide how interrupted in-flight network requests should be represented.
