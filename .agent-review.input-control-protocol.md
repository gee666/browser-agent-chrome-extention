# Review: `browser-agent-ext/lib/input-control-protocol`

## Scope

Reviewed the protocol/spec package at `browser-agent-ext/lib/input-control-protocol` as a documentation-driven contract repository. The package is primarily prose/specification plus example payloads, so this review focuses on contract correctness, consistency across documents, cancellation/concurrency semantics, maintainability, and compliance/testability.

## Summary

The main risks are **spec contradictions** rather than implementation bugs inside this repo. Several core documents disagree on what is valid on the wire, especially around **`cancel`**, **request validation**, **ordering**, and **extensibility**. Those inconsistencies are serious because third-party implementations could each be “following the docs” and still become incompatible with one another.

---

## Critical

### 1. `cancel` response ordering is self-contradictory ✅
- **Files:**
  - `browser-agent-ext/lib/input-control-protocol/PROTOCOL.md`
  - `browser-agent-ext/lib/input-control-protocol/COMMANDS.md`
  - `browser-agent-ext/lib/input-control-protocol/TRANSPORTS.md`
- **Problem:**
  - `PROTOCOL.md` states that responses are sent **"exactly one response per request in request order"**.
  - But `COMMANDS.md` shows `cancel` responding immediately with its own `ok` response **before** the earlier in-flight command returns `"Command cancelled"`.
  - `TRANSPORTS.md` also describes `cancel` as something that interrupts an in-flight command while still returning its own response promptly.
- **Why this matters:**
  - A client cannot reliably reason about stop/cleanup behavior if one implementation emits responses strictly in request order and another emits the `cancel` acknowledgment first.
  - This is a protocol-level ambiguity, not a documentation nit. It affects interop, pending-request bookkeeping, and shutdown logic.
- **Recommendation:**
  - Define one explicit rule and apply it everywhere:
    - either **strict request-order responses**, where the cancelled command response is emitted before the `cancel` ack,
    - or **special-case control-plane ordering**, where `cancel` is allowed to acknowledge immediately ahead of the cancelled command.
  - If `cancel` is special, say so clearly in `PROTOCOL.md` and state that request-order guarantees apply only to action commands.

### 2. The canonical request schema cannot represent documented `cancel` traffic or the documented unknown-command path ✅
- **Files:**
  - `browser-agent-ext/lib/input-control-protocol/PROTOCOL.md`
  - `browser-agent-ext/lib/input-control-protocol/COMMANDS.md`
  - `browser-agent-ext/lib/input-control-protocol/ERRORS.md`
  - `browser-agent-ext/lib/input-control-protocol/examples/cancel_ok_request.json`
  - `browser-agent-ext/lib/input-control-protocol/examples/unknown_command_error_request.json`
- **Problem:**
  - `PROTOCOL.md`'s request JSON Schema enumerates only the 8 action commands and excludes `cancel`.
  - However, `COMMANDS.md` documents `cancel` as a real request shape with `{id, command, params, context}` and ships examples for it.
  - Separately, the same schema makes the documented `Unknown command: <name>` error path unreachable for schema-first implementations, because any unknown command would fail schema validation before it could hit unknown-command handling.
- **Why this matters:**
  - Machine-generated validators and independent implementations will diverge immediately.
  - A schema consumer will reject payloads that the rest of the spec says are valid (`cancel`) and may emit the wrong class of error for unsupported commands.
- **Recommendation:**
  - Choose one model and make all artifacts match:
    1. Include `cancel` in the canonical request command set and define unknown-command handling outside the schema layer, or
    2. Keep `cancel` transport-only but remove it from `COMMANDS.md` examples and define a separate transport-frame schema.
  - Also decide whether unknown commands are a schema error or dispatcher error, then align `PROTOCOL.md`, `ERRORS.md`, and examples.

## High

### 3. `context` translation guidance is inconsistent with the referenced ground truth and can cause incorrect clicks ✅
- **Files:**
  - `browser-agent-ext/lib/input-control-protocol/CONTEXT.md`
  - `browser-agent-ext/lib/input-control-protocol/BACKENDS.md`
  - Referenced implementation area: `python-input-control/src/python_input_control/platform.py`
- **Problem:**
  - `CONTEXT.md` sketches physical translation using `scrollOffsetX` and warns that scrolling between capture and dispatch skews translation.
  - But the referenced implementation's `translate_viewport_to_physical_screen(...)` does **not** use `scrollX`/`scrollY` in coordinate translation.
- **Why this matters:**
  - A third-party OS backend following the prose literally could add scroll offsets and systematically mis-target pointer events on scrolled pages.
  - Because this package positions the Python host as ground truth, conflicting guidance in the protocol docs is especially risky.
- **Recommendation:**
  - Either update the docs to match the reference implementation exactly, or explicitly call out `scrollX`/`scrollY` as informational/not used for coordinate translation in v1.
  - If the current implementation is actually incomplete, then the spec should say so and the reference host should be updated before claiming the shape is frozen.

### 4. `params` forward-compatibility rules conflict with every per-command schema ✅
- **Files:**
  - `browser-agent-ext/lib/input-control-protocol/PROTOCOL.md`
  - `browser-agent-ext/lib/input-control-protocol/COMMANDS.md`
- **Problem:**
  - `PROTOCOL.md` says unknown `params` keys **SHOULD be ignored**.
  - Every command schema in `COMMANDS.md` uses `"additionalProperties": false`, which means unknown keys should be rejected.
- **Why this matters:**
  - This breaks the repo's own versioning story. The README says a minor version may add optional fields while existing clients keep working, but strict schema validators generated from the command docs will reject those fields.
  - It also creates avoidable implementation drift: some ports will ignore unknown keys, others will reject them.
- **Recommendation:**
  - Pick one extensibility rule:
    - **Strict schemas:** reject unknown keys everywhere and remove the "SHOULD be ignored" language.
    - **Forward-compatible schemas:** allow additional properties or define a per-command extension namespace.
  - Whatever is chosen should be stated once in `PROTOCOL.md` and reflected mechanically in command schemas.

### 5. Transport compliance requirements contradict the package’s own compatibility claim ✅
- **Files:**
  - `browser-agent-ext/lib/input-control-protocol/README.md`
  - `browser-agent-ext/lib/input-control-protocol/TRANSPORTS.md`
- **Problem:**
  - `README.md` says any implementation that accepts the same envelope shape and emits the same response envelope is protocol-compatible.
  - `TRANSPORTS.md` says both native messaging and in-process direct call are normative for v1 and are **required to be supported by any v1 implementation**.
- **Why this matters:**
  - Those statements describe different standards: one is envelope compatibility, the other is transport matrix compliance.
  - A third-party backend supporting only one transport would be both “compatible” and “non-compliant,” which is confusing for implementers and consumers.
- **Recommendation:**
  - Split the concepts explicitly:
    - **Protocol-compatible:** same envelope/semantics.
    - **Full v1 reference-profile compliant:** supports specified transport set.
  - Or redefine transports as informative capability profiles rather than universal requirements.

### 6. Cancellation cleanup for stateful input is under-specified ✅
- **Files:**
  - `browser-agent-ext/lib/input-control-protocol/COMMANDS.md`
  - `browser-agent-ext/lib/input-control-protocol/BACKENDS.md`
  - Reference implementation areas:
    - `browser-agent-ext/lib/browser-agent-input-control/src/backends/mouse.js`
    - `python-input-control/src/python_input_control/backends/pyautogui_mouse_backend.py`
- **Problem:**
  - The spec requires commands to be cancellable, but does not define what must happen if cancellation occurs after a mouse button or modifier key has already been pressed.
  - The referenced mouse implementations have a pattern like: press -> cancellable wait -> release. A cancel during the wait can bypass the release.
- **Why this matters:**
  - This creates a real stuck-input risk: a backend could leave a mouse button or keyboard modifier logically held after returning `"Command cancelled"`.
  - That kind of state leak is severe for automation systems and difficult to diagnose.
- **Recommendation:**
  - Add an explicit backend requirement: **on cancellation or exception, any currently held buttons/keys MUST be released before returning**.
  - Consider a short section covering idempotent cleanup and best-effort release semantics for `mouse_click` and `press_shortcut`.

## Medium

### 7. The spec package lacks an executable compliance suite, making doc drift likely ✅
- **Files/areas:**
  - `browser-agent-ext/lib/input-control-protocol/`
  - `browser-agent-ext/lib/input-control-protocol/examples/`
- **Problem:**
  - The repo provides prose and example JSON pairs, but no machine-checked compliance tests, no standalone generated schema artifacts, and no validation that examples are consistent with the written schemas.
- **Why this matters:**
  - The contradictions above are exactly the kind of regressions that an executable spec harness would catch early.
  - Since this repo appears intended as a canonical contract package, drift between docs, examples, and referenced implementations is the primary maintenance risk.
- **Recommendation:**
  - Add a small spec test harness that at minimum verifies:
    - example requests/responses parse and validate,
    - documented command names align across files,
    - error examples match documented error categories,
    - request/response ordering and cancellation semantics are asserted in one place.
  - Consider producing canonical JSON Schemas from a single source rather than hand-maintaining repeated snippets.

### 8. Error documentation is not internally complete for width-related context validation ✅
- **Files:**
  - `browser-agent-ext/lib/input-control-protocol/ERRORS.md`
  - `browser-agent-ext/lib/input-control-protocol/CONTEXT.md`
  - `browser-agent-ext/lib/input-control-protocol/BACKENDS.md`
- **Problem:**
  - `CONTEXT.md` and `BACKENDS.md` describe width validation rules and mention messages like:
    - `Browser widths must be greater than or equal to zero`
    - `Field 'context.outerWidth' must be greater than or equal to 'context.innerWidth'`
  - But `ERRORS.md`'s main validation table only lists the height variants, not the width variants.
- **Why this matters:**
  - Implementers using `ERRORS.md` as the canonical error catalogue can miss legitimate protocol strings.
  - This is smaller than the contradictions above, but it still weakens the “verbatim message” contract.
- **Recommendation:**
  - Make `ERRORS.md` exhaustive or clearly mark it as a non-exhaustive summary.
  - Prefer generating the error catalogue from a single source if exact strings are considered normative.

---

## Low

### 9. Repeated inline schema snippets increase maintenance cost and inconsistency risk ✅
- **Files/areas:**
  - `browser-agent-ext/lib/input-control-protocol/PROTOCOL.md`
  - `browser-agent-ext/lib/input-control-protocol/COMMANDS.md`
  - `browser-agent-ext/lib/input-control-protocol/ERRORS.md`
  - `browser-agent-ext/lib/input-control-protocol/CONTEXT.md`
- **Problem:**
  - Command names, field rules, and exact error strings are repeated across multiple markdown files.
  - The current inconsistencies suggest the package has no single authoritative source for schema and semantics.
- **Why this matters:**
  - Even small future updates are likely to produce more drift across docs, examples, and implementations.
  - This is a maintainability problem more than an immediate bug.
- **Recommendation:**
  - Centralize command metadata in one source file and generate the markdown tables/snippets/examples where possible.
  - At minimum, define one file as authoritative for command set, field rules, and error strings, and link to it rather than duplicating content.

---

## Suggested next steps

1. Resolve the `cancel` contract first: request validity, ordering, and cleanup semantics.
2. Decide whether schemas are strict or forward-compatible, then align all command schemas and examples.
3. Reconcile `context` translation guidance with the reference implementation before more third-party backends are built.
4. Add an executable compliance check so future edits cannot reintroduce these contradictions.

## Notes

- This review focused on the protocol/spec package itself, not on making changes in sibling implementation repos.
- I referenced sibling implementation areas only where the spec explicitly points to them as the ground truth or where they materially clarify protocol risk.
