## High

### 1. Cancellation can break command serialization and allow overlapping real input ✅
- **Files:** `src/python_input_control/protocol.py:183-190`
- **What happens:** On a `{"command": "cancel"}` message, the host sets `cancel_event`, waits only `join(timeout=1.0)`, then immediately clears the cancel flag and drops the thread reference with `current_cmd_thread = None`.
- **Why this is risky:** If the running backend is blocked in an uninterruptible operation, or simply takes longer than one second to observe cancellation, the old command thread can continue emitting OS-level mouse/keyboard input after the host has already acknowledged cancel and accepted a new command.
- **Impact:** The repo intends commands to remain serialized, but in this case two commands can overlap in wall-clock time. That is especially dangerous for a native input controller because it can produce interleaved clicks/keystrokes against the wrong UI state.
- **Suggested direction:** Do not clear the cancel flag or null out `current_cmd_thread` until the command thread has actually exited. If bounded cancellation is required, the protocol should surface a distinct “cancel requested but command still running” state instead of pretending cancellation completed.
- **Testing gap:** There is no protocol test that simulates a command thread that ignores cancellation for longer than the 1 second join timeout.

### 2. Queued normal commands can block later cancel/EOF processing ✅
- **Files:** `src/python_input_control/protocol.py:193-198`
- **What happens:** The main loop reads messages from the queue, but when it dequeues a regular command while a prior command thread is still alive, it immediately blocks on `current_cmd_thread.join()`.
- **Why this is risky:** If the sender pipelines messages as `A`, `B`, then `cancel`, the host can dequeue `B` first and block waiting for `A` to finish before it ever consumes the queued `cancel` or EOF sentinel.
- **Impact:** This contradicts the stated design in the `serve_forever()` docstring that cancel/disconnect is noticed promptly while a command is running. In practice, prompt cancellation depends on queue ordering and timing, which is fragile.
- **Suggested direction:** Separate “inbox draining” from “command scheduling”. For example, keep reading queue items while a command is active, record cancellation/EOF immediately, and only start the next regular command after the active one is truly done.
- **Testing gap:** `tests/test_protocol.py` covers back-to-back command ordering, but not the race where a regular command is queued ahead of a later cancel.

## Medium

### 3. `pause` is not cancellation-aware, making sequences partially unabortable ✅
- **Files:** `src/python_input_control/dispatch.py:123-124`
- **What happens:** `PauseCommand` directly calls `self.runtime.sleep(...)`, while the keyboard and mouse backends use cancel-aware sleep helpers that raise `CommandCancelledError` when `cancel_event` fires.
- **Why this is risky:** A long `pause` inside `sequence` cannot be interrupted promptly. That makes the protocol-level cancellation behavior inconsistent across command types.
- **Impact:** Users can stop typing/mouse motion promptly, but not a long pause. Combined with the protocol issues above, this makes cancellation semantics unreliable in real workflows.
- **Suggested direction:** Reuse the same cancel-aware sleep abstraction across all command types, including `pause`.
- **Testing gap:** There is no test verifying that cancelling a sequence containing a long pause exits promptly.

### 4. Protocol input buffering is unbounded ✅
- **Files:** `src/python_input_control/protocol.py:112-128`
- **What happens:** The stdin reader thread pushes frames into an unbounded `queue.SimpleQueue` while command execution happens elsewhere. Individual frames may be up to 4 MB.
- **Why this is risky:** A buggy or malicious client can keep writing framed messages faster than the dispatcher can consume them, causing unbounded in-process memory growth.
- **Impact:** The host is intended to be long-lived and attached to a browser extension; lack of backpressure can turn a client-side bug into a host memory problem.
- **Suggested direction:** Use a bounded queue and define explicit backpressure behavior, or reject/close on excessive queued work.
- **Testing gap:** No tests stress queue growth or verify host behavior under write bursts while a long-running command is active.

### 5. Manifest updates are non-atomic and can lose concurrent changes ✅
- **Files:** `src/python_input_control/installer.py:399-401`, `src/python_input_control/installer.py:479-544`
- **What happens:** `allow_command()` and `disallow_command()` perform a read/modify/write cycle on the manifest and persist it with a direct `write_text()`.
- **Why this is risky:** Concurrent invocations can overwrite each other’s changes. Readers may also observe partially written JSON if they open the file during a write.
- **Impact:** Extension authorization state can be lost or temporarily corrupted, especially in automation or installer scripts run from multiple processes.
- **Suggested direction:** Write to a temporary file and atomically replace the manifest, ideally with file locking around the read/modify/write sequence.
- **Testing gap:** Existing installer tests cover functionality well, but not concurrent mutation or atomicity guarantees.

### 6. Protocol refactor introduced an error-logging regression, and the suite is already red because of it ✅
- **Files:** `src/python_input_control/protocol.py:203-221`, `tests/test_protocol.py:321-345`
- **What happens:** `_run_command()` now calls `dispatcher.handle_message()` and writes the response, but no longer logs `response.error`. The old behavior still exists only in `_handle_payload()`, which is no longer used by `serve_forever()`.
- **Evidence:** `pytest -q` currently fails on `test_host_returns_error_for_pointer_command_when_bounds_are_unavailable` because stderr is empty instead of containing the expected error log line.
- **Impact:** Host-side diagnostics became less useful after the threaded protocol refactor, and the main branch currently ships with a failing test.
- **Suggested direction:** Either restore logging in `_run_command()` or remove the dead `_handle_payload()` path and centralize response/error logging in one place.
- **Maintainability note:** Keeping the obsolete `_handle_payload()` method alongside the new threaded flow increases the chance of future behavior drifting again.

### 7. Virtual desktop bounds are cached for the full process lifetime ✅
- **Files:** `src/python_input_control/platform.py:130-160`
- **What happens:** Windows, macOS, and Linux virtual desktop bound lookups are all decorated with `@lru_cache(maxsize=1)`.
- **Why this is risky:** Monitor hot-plugging, display arrangement changes, scaling changes, or a transient startup detection failure can leave pointer validation stale for the rest of the host process lifetime.
- **Impact:** Commands may be rejected incorrectly, or validated against old geometry after the desktop changes.
- **Suggested direction:** Either make the cache time-bounded/invalidation-aware or recalculate bounds on demand for pointer commands.
- **Testing gap:** Current tests validate parsing and basic bounds behavior, but not runtime display changes or recovery from an initial `None` result.

## Low

### 8. `protocol.py` mixes queueing, lifecycle, cancellation, logging, and response writing in one method ✅
- **Files:** `src/python_input_control/protocol.py:77-210`
- **What happens:** `NativeMessagingHost.serve_forever()` contains framing/error handling, queue orchestration, command-thread lifecycle, cancellation semantics, EOF handling, and response writing in one large control-flow block.
- **Why this matters:** The recent logging regression is a good example of how behavior can drift when protocol responsibilities are duplicated or only partially moved during refactors.
- **Impact:** This area is harder to reason about and harder to test exhaustively, especially for races.
- **Suggested direction:** Split the protocol host into smaller units, e.g. frame reader, scheduler/state machine, and response/logging policy. That would also make race-oriented tests more targeted.

---

## Overall assessment

The project is generally in good shape on input validation and basic test coverage, but the **threaded native-messaging protocol path is the highest-risk area**. The main concerns are:
1. cancellation semantics are not actually reliable under queueing and slow/uninterruptible commands,
2. protocol diagnostics regressed during refactoring, and
3. stateful file updates in the installer are not safe under concurrency.

If I were prioritizing fixes, I would address them in this order:
1. protocol cancellation/serialization correctness,
2. protocol logging regression + dead code cleanup,
3. manifest write atomicity,
4. cancellation-aware `pause`,
5. queue backpressure and display-bounds cache strategy.
