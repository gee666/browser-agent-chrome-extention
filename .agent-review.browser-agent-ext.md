## High

### 1. Vision screenshots can come from the wrong tab ✅

**Files / symbols**
- `browser-agent-ext/background/pi-bridge-runtime.js` — `createAgentBrowserBridge()`
- `browser-agent-ext/lib/browser-agent-core/background/browser-bridge.js` — `takeScreenshot()`
- `browser-agent-ext/lib/browser-agent-core/background/agent.js` — calls to `this._bridge.takeScreenshot()`

**What is wrong**

`createAgentBrowserBridge()` overrides `getActiveTabId()` and `navigate()` so task actions target the dedicated task tab, but it does **not** override `takeScreenshot()`. The inherited `BrowserBridge.takeScreenshot()` still uses `chrome.tabs.captureVisibleTab(...)`, which captures the currently visible tab in the window rather than the task tab.

**Why it matters**

- If the user switches tabs while a task is running, input can still be sent to the task tab while screenshots come from a different tab.
- With vision enabled, the LLM can reason over unrelated content and make incorrect decisions.
- This is also a privacy risk: a non-task tab can be unintentionally sent to the model.

**Recommendation**

Make screenshot capture tab-scoped in the extension adapter instead of inheriting `captureVisibleTab()` semantics. The cleanest fix is to implement a task-tab-aware `takeScreenshot()` in `createAgentBrowserBridge()` using the existing CDP-based capture path (or another explicit per-tab mechanism), and treat screenshotting as part of the bridge contract rather than an implicit inherited behavior.

### 2. Stop/cancel is not reliably honored during startup ✅

**Files / symbols**
- `browser-agent-ext/background/sw.js` — `stopCurrentTask()`
- `browser-agent-ext/background/sw.js` — `startAgentTask()`

**What is wrong**

`stopCurrentTask()` sets `taskRun.cancelRequested = true`, but `startAgentTask()` only checks that flag once, immediately after `loadAgentConfig()`. There are several awaited startup steps after that check:

- `piBridgeRuntime.resolveRunTaskTab(...)`
- `piBridgeRuntime.createAgentBrowserBridge(...)`
- optional initial `bridge.navigate(url)`
- input-control construction / agent construction

If the user clicks Stop during those awaits, the task can still proceed into `currentAgent.run(task)`.

**Why it matters**

- A cancelled task may still navigate tabs, arm debugger state, and begin execution.
- This is most visible on slow tab resolution or slow initial navigation.
- It also makes the popup’s stop UX misleading: the UI can show a stop request while the task still starts running.

**Recommendation**

Re-check cancellation after each awaited startup phase, or centralize startup in a small helper that throws a cancellation error whenever `cancelRequested` becomes true. The initial navigation path especially needs a cancellation gate before creating/running `AgentCore`.

## Medium

### 3. Anthropic OAuth is effectively broken in the Options UI ✅

**Files / symbols**
- `browser-agent-ext/options/options.js` — `OAUTH_KEY_MAP`, `refreshOAuthStatus()`, `updateOAuthUI()`, `handleOAuthResult()`
- `browser-agent-ext/options/options.html` — Anthropic OAuth controls (`login-anthropic`, `logout-anthropic`, `badge-anthropic`, `status-anthropic`, `detail-anthropic`)

**What is wrong**

The JS uses `uiKey = 'anthropic-oauth'` when building DOM IDs, so it looks for elements like:

- `login-anthropic-oauth`
- `badge-anthropic-oauth`
- `status-anthropic-oauth`

But the HTML defines Anthropic controls with `anthropic`, not `anthropic-oauth`:

- `login-anthropic`
- `badge-anthropic`
- `status-anthropic`

As a result, Anthropic login/logout listeners are never attached and status updates do not render against the actual Anthropic card.

**Why it matters**

The Anthropic OAuth flow exists in the background worker, but the main settings page cannot drive it correctly, so users are likely to conclude the feature is broken.

**Recommendation**

Separate **provider IDs** from **UI element IDs**. A small normalized auth-provider config object would avoid this class of mismatch entirely.

### 4. OAuth callback validation accepts a missing `state` value ✅

**Files / symbols**
- `browser-agent-ext/background/sw.js` — `chrome.webNavigation.onBeforeNavigate` OAuth callback handler

**What is wrong**

The callback only rejects when:

```js
if (state && pending.state && state !== pending.state)
```

That means a redirect with **no `state` at all** is accepted, even though a `pending.state` was generated and stored before opening the auth tab.

**Why it matters**

This weakens the intended CSRF protection model. A valid OAuth callback should require the returned `state` to match the stored `pending.state`, not merely reject mismatches when `state` happens to be present.

**Recommendation**

Require strict equality when a pending state exists. Missing state should fail closed.

### 5. `browser_get_html` validates `max_bytes`, but the runtime ignores it ✅

**Files / symbols**
- `browser-agent-ext/lib/pi-browser-agent-bridge/src/handlers/read-only/index.js` — `htmlHandler()`
- `browser-agent-ext/background/pi-bridge-runtime.js` — `collectHtml()` and the `getHtml` dependency wiring in `createReadOnlyHandlers(...)`

**What is wrong**

The bridge handler layer normalizes and forwards `max_bytes`, and tests assert that behavior, but the extension runtime drops it:

- handler forwards `maxBytes`
- runtime `getHtml` implementation only passes `{ selector, selectorAll, strip }`
- `collectHtml()` returns full `outerHTML` with no truncation or limit enforcement

**Why it matters**

- Large pages can return arbitrarily large HTML blobs over the bridge.
- That diverges from the public bridge contract.
- It increases memory/transport risk and makes behavior unpredictable for remote callers.

**Recommendation**

Enforce the limit in the runtime path that actually extracts HTML, and add an integration test at the extension layer so the contract is verified end-to-end rather than only at the handler stub boundary.

## Low

### 6. The extension glue depends on private / internal submodule contracts ✅

**Files / symbols**
- `browser-agent-ext/background/sw.js` — `summarizeAgentHistory()` reading `agent._history`
- `browser-agent-ext/background/sw.js` — mutating the `status` object in `onStatus`
- `browser-agent-ext/background/pi-bridge-runtime.js` — direct imports from `../lib/pi-browser-agent-bridge/src/...`

**What is wrong**

The integration layer is reaching across package boundaries in a few places:

- it reads `AgentCore` private state (`_history`)
- it relies on mutating the status object passed from `AgentCore`
- it imports deep internal files from `pi-browser-agent-bridge/src/...` rather than a narrow public API

**Why it matters**

This makes refactoring the submodules riskier than it should be. Internal changes in the child repos can break the extension even when the intended public behavior has not changed.

**Recommendation**

Promote the required hooks to explicit public interfaces:

- expose history/status summaries from `browser-agent-core`
- stop mutating callback payloads in-place
- re-export bridge primitives from package entry points instead of importing internals from `src/`

### 7. The extension-specific glue has very little direct test coverage ✅

**Files / areas**
- Extension root tests: `browser-agent-ext/background/task-lifecycle.test.js`
- Missing direct coverage for:
  - `browser-agent-ext/background/sw.js`
  - `browser-agent-ext/background/pi-bridge-runtime.js`
  - `browser-agent-ext/options/options.js`
  - `browser-agent-ext/popup/popup.js`

**What is wrong**

Most existing test depth is in the shared libraries (`lib/pi-browser-agent-bridge`, `lib/browser-agent-input-control`, `lib/browser-agent-core`). The extension root itself has only a very small task-lifecycle unit test.

**Why it matters**

Several of the concrete regressions above live exactly in this untested glue layer:

- startup cancellation race
- Anthropic OAuth DOM wiring bug
- end-to-end contract drift between handler validation and runtime HTML extraction

**Recommendation**

Add a thin but focused extension-level test layer around:

- service-worker task startup/stop behavior
- OAuth UI wiring and status rendering
- `createPiBridgeRuntime()` handler wiring for `browser_get_html` and screenshots

## Positive notes

- The shared CDP session management (`CdpInspector`) and the dedicated `browser-agent-input-control` package are good building blocks.
- `lib/pi-browser-agent-bridge` has meaningful unit coverage around dispatcher and lifecycle behavior.
- The repo decomposition into core agent, input control, and bridge packages is directionally strong; most issues are in the integration layer rather than the core split itself.
