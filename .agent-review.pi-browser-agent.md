# Review: `pi-browser-agent`

Repository reviewed: `./pi-browser-agent`

## Scope and approach

I reviewed the broker lifecycle, tool registration flow, task persistence, public tool implementations, and the current test suite.

Validation performed:
- Read the core implementation under `src/`
- Read the current tests under `tests/`
- Ran `node --test ./tests/*.test.ts ./tests/tools/*.test.ts` inside `pi-browser-agent` (`36/36` passing)

## Summary

The codebase is small and understandable, but there are several important lifecycle and contract issues around broker ownership, bridge handoff, and tool activation.

The biggest theme is **inconsistent ownership/state transitions**:
- the broker is process-global but session hooks behave like it is session-scoped
- the bridge handoff path can invalidate a healthy connection too early
- the extension entrypoint, README, and meta-tool disagree on when browser tools should be registered

## High

### 1) New connections can knock out the active bridge before they prove they are the replacement ✅
- **Files:** `pi-browser-agent/src/broker/server.ts`
- **Relevant areas:** `handleConnection()`, `failBridge()`, `handleRawMessage()`

#### Why this matters
In `handleConnection()`, any newly accepted socket immediately causes the current bridge to be failed if `this.bridgeSocket` already exists:
- `server.ts`: `if (this.bridgeSocket && this.bridgeSocket !== socket) { ... }`
- it calls `this.failBridge(this.bridgeSocket as BridgeSocket, new Error('E_BRIDGE_DISCONNECTED'))`
- but the new socket is not promoted to the bridge until it later sends a valid `hello` frame in `handleRawMessage()`

That means a stray local client, a half-open reconnect, or a buggy extension reconnect can drop the active bridge and reject all in-flight requests **before** the replacement has authenticated as the new bridge.

#### Additional bug in the same path
The code tries to close the old bridge after calling `failBridge()`, but `failBridge()` nulls `this.bridgeSocket` first. The subsequent close runs against `null`, so the stale socket is not actually closed.

#### Impact
- in-flight tool calls can fail spuriously
- a temporary reconnect can cause a full disconnect instead of a seamless handoff
- stale sockets remain alive longer than intended, making lifecycle/debugging harder

#### Recommended fix
- Only replace the current bridge **after** the new socket sends a valid `hello`
- Keep a local reference to the old socket before clearing state, then close that explicit reference
- Treat “connected TCP socket” and “accepted bridge session” as different states

### 2) Broker creation is race-prone, and failed brokers can overwrite healthy ones ✅
- **Files:** `pi-browser-agent/src/index.ts`, `pi-browser-agent/src/broker/server.ts`
- **Relevant areas:** `getOrCreateBroker()`, `BrowserAgentBroker.start()`

#### Why this matters
`getOrCreateBroker()` assigns `brokerSingleton` **after** awaiting `broker.start()`.

At the same time, `BrowserAgentBroker.start()` catches startup failures internally and stores them in `startupError` instead of throwing.

That combination creates a bad concurrency window:
1. two overlapping `session_start` flows both see `brokerSingleton === null`
2. both construct brokers and call `start()`
3. one broker may actually bind successfully while the other records `EADDRINUSE`
4. whichever call returns last overwrites `brokerSingleton`

The process can then end up holding a singleton that is not listening, while the actually-listening broker is orphaned.

#### Impact
- inconsistent startup/shutdown behavior
- leaked broker instances
- confusing recovery after transient bind conflicts
- hard-to-reproduce failures if pi ever runs overlapping session starts in one process

#### Recommended fix
- Serialize broker creation with a module-scope promise/mutex
- Only publish a broker as the singleton after successful listen/bind
- Prefer making `start()` throw on fatal startup failures instead of silently storing them as internal state

### 3) Tool activation behavior is internally contradictory: entrypoint eagerly registers tools, while docs and the meta-tool describe lazy activation ✅
- **Files:**
  - `pi-browser-agent/README.md`
  - `pi-browser-agent/src/index.ts`
  - `pi-browser-agent/src/tools/browser_agent_tools.ts`
  - `pi-browser-agent/tests/index.test.ts`
  - `pi-browser-agent/tests/tools/meta-tool.test.ts`

#### Why this matters
The README says:
- the extension exposes only `activate_browser_agent_tools` first
- the full `browser_*` suite is registered only after the bridge is reachable

The meta-tool implementation also enforces that model: it refuses registration when `probe.bridgeConnected` is false.

But `src/index.ts` does something different on `session_start`:
- it registers the meta-tool
- then it immediately calls `registerAllTools(pi, { broker })` whenever `probe.brokerListening` is true
- it does **not** require `probe.bridgeConnected`

The tests reinforce the contradiction:
- `tests/index.test.ts` expects `browser_run_task` to already exist right after `session_start`
- `tests/tools/meta-tool.test.ts` expects no registration when the bridge is absent

#### Impact
- sessions can advertise tools that are not actually usable yet
- the activation story is confusing for users and future maintainers
- docs, tests, and runtime behavior are drifting apart

#### Recommended fix
Pick one activation model and make all layers agree.

The cleanest fit for this repo is:
- register only `activate_browser_agent_tools` on session start
- register the full suite only after a healthy bridge check succeeds
- update `tests/index.test.ts` to match the intended lazy-registration contract

## Medium

### 4) `request()` can convert immediate bridge disconnects into slow timeouts ✅
- **Files:** `pi-browser-agent/src/broker/server.ts`
- **Relevant area:** `request()`

#### Why this matters
`request()` first checks that `this.bridgeSocket` exists, but it later sends with optional chaining:
- `this.bridgeSocket?.send(payload)`

If the bridge disconnects after the initial check but before the send, the send becomes a no-op, the pending request stays in `pendingRequests`, and the caller waits until timeout instead of getting a direct disconnect error.

#### Impact
- intermittent timeout errors instead of precise transport failures
- slower recovery paths
- harder production diagnosis under reconnect/load

#### Recommended fix
Capture the socket in a local variable after validation and send through that stable reference. If the send cannot happen, reject immediately with `E_BRIDGE_DISCONNECTED`.

### 5) Observability tools throw exceptions, unlike the rest of the tool surface ✅
- **Files:**
  - `pi-browser-agent/src/tools/browser_observability_tools.ts`
  - `pi-browser-agent/tests/tools/browser-observability-tools.test.ts`

#### Why this matters
`browser_get_console_logs` and `browser_get_network` call `requestBridge()` directly and do not catch failures. By contrast, the read-only, JS/navigation, and task tools generally convert failures into structured `{ details: { ok: false, error } }` results.

The current test suite even codifies this inconsistency by expecting `browser_get_network` to reject.

#### Impact
- callers need per-tool error handling instead of one uniform contract
- disconnect/timeouts can bubble out as thrown errors only for some tools
- the public API is harder to use correctly

#### Recommended fix
Normalize observability tools to the same structured-result contract used elsewhere, then update the tests to assert that shape.

### 6) `browser_clear_site_data` can send ambiguous target parameters ✅
- **Files:** `pi-browser-agent/src/tools/browser_js_navigation_tools.ts`, `pi-browser-agent/tests/tools/browser-js-navigation-tools.test.ts`
- **Relevant areas:** `withDefaultActiveTabTarget()`, `createRequestTool()`, `browserClearSiteDataDefinition`

#### Why this matters
`browser_clear_site_data` supports explicit targets like `origin` and `url`, 
but it is still routed through `withDefaultActiveTabTarget()`.

That helper only suppresses the active-tab default when `tab_id` or `use_active_tab` is already set. So a call like:
- `{ origin: 'https://example.com' }`

becomes:
- `{ origin: 'https://example.com', use_active_tab: true }`

The tests currently expect this behavior.

#### Impact
- ambiguous request semantics
- bridge-side conflicts if both “explicit origin” and “active tab” are treated as selectors
- risk of clearing the wrong site data

#### Recommended fix
Treat `origin` and `url` as explicit targeting inputs for `browser_clear_site_data`, and do not inject `use_active_tab` when either is present.

### 7) Several success paths are too trusting of malformed bridge payloads ✅
- **Files:**
  - `pi-browser-agent/src/tools/browser_task_tools.ts`
  - `pi-browser-agent/src/tools/read_only/index.ts`
  - `pi-browser-agent/src/tools/browser_js_navigation_tools.ts`

#### Why this matters
There are multiple places where malformed “success” payloads are accepted instead of treated as protocol errors:

- `browser_task_tools.ts`
  - `terminalStatusOf()` defaults missing status to `'done'`
  - a bridge response like `{ ok: true, data: {} }` can be recorded as a completed task
- `read_only/index.ts`
  - `browser_get_html` falls back to `''` if neither `html` nor `content` is present and still returns `ok: true`
- `browser_js_navigation_tools.ts`
  - success text falls back to `unknown`, `unknown URL`, or `unknown origin` instead of validating required fields

#### Impact
- bridge regressions can look like success
- task history can become misleading
- downstream agents/tools lose signal when the protocol drifts

#### Recommended fix
Add minimal per-tool response validation before reporting success. This does not need a huge schema layer; even a few targeted guards would catch most drift.

### 8) Task-history corruption handling is inconsistent and can break list operations ✅
- **Files:**
  - `pi-browser-agent/src/broker/task-store.ts`
  - `pi-browser-agent/src/tools/browser_task_tools.ts`

#### Why this matters
`TaskStore.read()` parses every JSONL line and throws on malformed content. `TaskStore.list()` uses `read()` directly, so one corrupted task file can fail `browser_list_tasks` entirely.

At the same time:
- `browser_get_task_history` uses `safeReadHistory()` and silently turns read failures into “not found”
- `gc()` catches read failures and treats the file as empty

So corruption is handled three different ways:
- hard failure in list
- silent not-found in history lookup
- silent cleanup behavior in GC

#### Impact
- local state corruption can take down task listing
- corrupted history can be misreported as missing history
- operator debugging becomes harder because the error is masked inconsistently

#### Recommended fix
Handle per-file corruption explicitly:
- isolate malformed files during `list()` instead of failing the whole result set
- surface a corruption marker/error in task details rather than “not found”
- keep GC behavior explicit and logged

## Low

### 9) `force_refresh` on the meta-tool is effectively a no-op ✅
- **Files:**
  - `pi-browser-agent/src/tools/browser_agent_tools.ts`
  - `pi-browser-agent/src/tools/_register.ts`
  - `pi-browser-agent/tests/tools/meta-tool.test.ts`

#### Why this matters
The meta-tool exposes a `force_refresh` parameter, which suggests tool definitions can be refreshed after reconnect/reload.

But `_register.ts` uses the module-global `registeredToolNames` set and skips any name that has already been registered. So `force_refresh: true` does not actually replace or re-register anything.

The current tests assert the no-op behavior.

#### Impact
- misleading public API
- reconnect/reload flows cannot truly refresh stale registrations

#### Recommended fix
Either:
- implement real refresh semantics, or
- remove/rename the parameter so the API does not promise behavior it cannot deliver

### 10) Important race/corruption scenarios are not covered by tests ✅
- **Files:** `pi-browser-agent/tests/**/*.test.ts`

#### Missing coverage I would add next
- overlapping `session_start` calls against `getOrCreateBroker()`
- a new socket connecting but never sending `hello`
- bridge handoff where the old socket must remain active until the new `hello` is accepted
- malformed success payloads for `browser_run_task`, `browser_get_html`, and JS/navigation tools
- corrupted `.jsonl` task-history files
- `browser_reload_extension` reconnect-timeout/failure path

#### Why this matters
The current suite is good for happy paths and several error cases, but it does not pin down the most failure-prone lifecycle transitions.

---

## Recommended priorities

1. Fix bridge handoff in `src/broker/server.ts`
2. Serialize broker creation and make startup ownership unambiguous
3. Resolve the lazy-vs-eager registration contract across `README`, `src/index.ts`, and tests
4. Standardize all tool families on one error contract
5. Add regression tests for the race conditions above
