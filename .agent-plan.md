# Implementation Plan — `pi-browser-agent` + `pi-browser-agent-bridge`

> This document is the single source of truth for the implementation. It
> contains every decision that has been made, every caveat worth knowing,
> the on-wire protocol, the list of tools and their full parameter
> schemas, the service-worker lifecycle handling, the build/test plan,
> and the rollout steps. A fresh agent given only this file should be
> able to ship the feature without asking further questions.

---

## 0. Goal

Add two repositories so that any pi session can drive the existing
`browser-agent-ext` Chrome extension:

1. **`pi-browser-agent`** — a pi extension (npm package,
   `pi.extensions: ["./src/index.ts"]`). Owns a local WebSocket broker
   and a suite of pi tools that the pi LLM can call.

2. **`browser-agent-ext/lib/pi-browser-agent-bridge`** — a plain-JS
   submodule loaded by the existing Chrome MV3 service worker. Connects
   out to the broker, maps incoming frames to `browser-agent-core`
   primitives + CDP collectors, and streams responses back.

Wire layout (Chrome on Windows or macOS or Linux, pi on the same host
or on a WSL distro next to a Windows Chrome — both are first-class
supported platforms):

```
pi tool (in a pi session)
    │ in-process
    ▼
pi-browser-agent (Node, starts broker)
    │ listens on ws://127.0.0.1:<port>   (loopback only)
    ▲
    │ JSON frames
    ▼
pi-browser-agent-bridge (inside browser-agent-ext SW)
    │ uses: browser-agent-core + chrome.debugger (CDP)
    ▼
Chrome tab(s)
```

MV3 rule respected — the extension only **connects out**, never listens.

## 1. Locked answers to open questions

These were decided by the user and are non-negotiable:

| # | Question                                              | Answer                                                                             |
|---|-------------------------------------------------------|------------------------------------------------------------------------------------|
| 1 | LLM for `run_task`                                    | Extension's own configured LLM. **Not** pi-brain.                                   |
| 2 | Tab policy                                            | Dedicated agent tab (pinned, titled `(pi agent)`); inspection tools can accept a `url`. |
| 3 | Broker transport                                      | WebSocket only. No HTTP.                                                           |
| 4 | Auth                                                  | Simple — loopback-only, no token by default.                                       |
| 5 | Platforms                                             | Windows, macOS, Linux, WSL→Windows. All first-class. Live streaming: **no**.       |
| 6 | Consent gates                                         | None. All tools including `evaluate_js` / `run_js` / `clear_site_data` are free.   |
| 7 | Screenshots                                           | Always compress (same compression as `browser-agent-core`: JPEG, max 1280 wide, q=0.7). |
| 8 | Task history retention                                | 7 days, auto-GC.                                                                   |
| 9 | LLM for the extension                                 | Separate setting, independent of pi's provider (user may want a cheaper one).      |
|10 | Tool names                                            | Long and self-documenting (`browser_get_html`, not `ba_html`).                     |
|+  | Long outputs                                          | Every tool that can return long data **must** apply `truncateHead`/`truncateTail`, write the full result to a temp file, and return the path in the tool text. Filters are optional params; the tool description must encourage the LLM to use them. |
|+  | Context-weight                                         | Only **one** meta-tool, `browser_agent_tools`, is registered at session start. The full 21-tool toolkit is registered lazily the first time that meta-tool is called and the broker is reachable. Sessions that never touch the browser pay ~1 tool description of context instead of ~21. See §6.0. |

## 3. `browser-agent-ext/manifest.json` changes

Required additions — union with existing:

```json
{
  "permissions": [
    "tabs", "activeTab", "scripting", "storage", "webNavigation",
    "nativeMessaging", "unlimitedStorage", "debugger", "alarms"
  ],
  "host_permissions": ["<all_urls>"]
}
```

`"alarms"` is new — needed to keep the SW alive across the 30 s idle
kill. `"webRequest"` is **not** added: CDP `Network.*` via
`chrome.debugger` covers everything, without enterprise-only
restrictions.

No new options page fields are required for auth (no token). The options
page gets:

- `piBridge.enabled` — bool, default `true`.
- `piBridge.url` — string, default `ws://127.0.0.1:7878`.

Stored in `chrome.storage.local` under `piBridgeConfig`.

## 4. Platform & transport details

- Broker **always** binds to `127.0.0.1:7878` (port configurable via
  `PI_BA_PORT`). This is enough for:
  - Windows-native pi ↔ Windows Chrome — same loopback.
  - macOS — same loopback.
  - Linux — same loopback.
  - WSL2 pi ↔ Windows Chrome — WSL2 auto-forwards loopback in both
    directions on supported Windows versions.
- If loopback forwarding is disabled by the user's WSL config, we
  detect it at broker startup:
  - Print a hint: *"If Chrome cannot connect, set the extension's
    bridge URL to `ws://<WSL IP>:7878` (see README)."*
  - Do **not** auto-bind to `0.0.0.0` — leave that as an explicit
    `PI_BA_HOST` override so we never expose input-control by default.
- State dir default:
  - Linux/WSL: `${XDG_STATE_HOME:-$HOME/.local/state}/pi-browser-agent`
  - macOS: `$HOME/Library/Application Support/pi-browser-agent`
  - Windows: `%LOCALAPPDATA%\pi-browser-agent`

## 5. Wire protocol

All frames are JSON text frames over a single WebSocket. Every frame
has `{ "v": 1, "kind": ... }`. Unknown kinds → error response. The
protocol is pinned at `v: 1` before shipping; the bridge refuses
connecting to a broker with a different major.

### 5.1 Bridge → broker frames
```
{ v:1, kind:"hello",    extensionId, version, capabilities:[...] }
{ v:1, kind:"response", id, ok:true,  data }
{ v:1, kind:"response", id, ok:false, error:{ code, message, details? } }
{ v:1, kind:"event",    topic, taskId?, payload }       # task_step, task_status, task_done, task_error
```

### 5.2 Broker → bridge frames
```
{ v:1, kind:"welcome",    brokerVersion, serverTime }
{ v:1, kind:"request",    id, type, params }
{ v:1, kind:"cancel",     id }                          # cancels one in-flight request
{ v:1, kind:"cancelTask", taskId }                      # stops a running run_task
```

### 5.3 Keep-alive
- WebSocket-level `ping` every 25 s from the broker.
- The bridge SW keeps itself alive with
  `chrome.alarms.create('pi-bridge-ka', { periodInMinutes: 0.4 })` and
  uses the alarm handler to `socket.send({kind:'ping'})`.

### 5.4 Error codes (canonical strings)
```
E_VALIDATION            # bad params
E_NO_ACTIVE_TAB         # no tab / tab gone
E_NAV_TIMEOUT           # navigation timed out
E_CDP_ATTACH            # debugger busy (DevTools open?)
E_ABORTED               # cancel honoured
E_BUSY                  # another task is running
E_UNKNOWN_TYPE          # unknown request.type
E_INTERNAL              # everything else
E_BRIDGE_DISCONNECTED   # ws dropped mid-request (broker-side only)
```

## 6. Tool catalogue (exhaustive)

### 6.0 Lazy registration via the `browser_agent_tools` meta-tool

**Problem.** A pi session that never needs the browser should not spend
context on 21 tool descriptions. The full toolkit is ~21 detailed
descriptions, many with rich parameter schemas — a non-trivial slice of
the context window.

**Solution.** pi's extension API supports runtime tool registration
(confirmed: `pi.registerTool()` works after startup, newly registered
tools are immediately callable in the same session without `/reload`;
`pi.setActiveTools()` can enable/disable tools at runtime). Exploit this:

1. At session start (`session_start` event), register **only**
   `browser_agent_tools`. Leave the other 20 tools unregistered and
   absent from the LLM's tool list.
2. When the LLM calls `browser_agent_tools`, its `execute` handler:
   a. Tries to connect to the broker (short timeout, e.g. 800 ms
      for an already-listening socket, one-shot `ws.open`).
   b. If the broker is **unavailable**: return a short text explaining
      the problem and the fix (install/start `pi-browser-agent`,
      load `browser-agent-ext`, …). Do **not** register the rest.
      Return includes a troubleshooting checklist (see below).
   c. If the broker is **available but the extension bridge hasn't
      connected yet** (broker running, no bridge client): return a
      similar "bridge not connected" message. Do **not** register.
   d. If **fully available** (broker + bridge hello exchanged and
      capabilities advertised): call the internal `registerAllTools()`
      helper, which uses `pi.registerTool()` to register every
      `browser_*` tool below. Idempotent — subsequent invocations
      see the registration is already done and skip it.
3. The `execute` return from `browser_agent_tools` is a text message
   that (on success) enumerates every newly-registered tool with its
   one-line purpose, so the LLM immediately knows what's available
   and can plan its next tool call. Example success payload:

   ```
   Browser agent is available and tools are now registered. The
   following browser_* tools are callable:

   - browser_run_task          Run a natural-language browser task end-to-end
   - browser_get_task_history  Retrieve step-by-step trace of a past task
   - browser_list_tasks        List recent browser tasks
   - browser_cancel_task       Cancel an in-flight browser task
   - browser_get_screenshot    Capture a compressed screenshot of a page (filters: selector, full_page)
   - browser_get_html          Extract HTML from a page (prefer selector filter)
   - browser_get_dom_info      Inspect a specific DOM element (selector required)
   - browser_get_computed_styles   Get computed CSS (prefer properties filter)
   - browser_get_console_logs      Read page console (prefer levels/substring/since filters)
   - browser_get_network           Read network requests (prefer filter.* params — status/type/url_contains)
   - browser_get_accessibility_tree Get the AX tree (prefer root_selector filter)
   - browser_get_performance_metrics  Performance and web-vitals
   - browser_evaluate_js       Evaluate a JS expression in the page
   - browser_run_js            Run a longer JS program; optionally capture console
   - browser_list_tabs         List open tabs
   - browser_switch_tab        Activate a tab
   - browser_close_tab         Close a tab
   - browser_navigate          Navigate a tab to a URL
   - browser_reload            Reload a tab
   - browser_wait_for          Wait for a selector/text/url condition
   - browser_clear_site_data   Clear cookies/storage for an origin

   Agent tab: <tabId> (<url>)
   Extension LLM provider: <provider>/<model>
   ```

   On unavailability, the failure payload is:

   ```
   Browser agent is not available. Reason: <short reason>.

   To fix:
     1. Make sure the broker is running: `pi-browser-agent` is installed
        as a pi extension — run any pi session and this starts the
        broker automatically on port <port>. Override with
        PI_BA_PORT=<n> if 7878 is busy.
     2. Load the Chrome extension browser-agent-ext (chrome://extensions
        → Load unpacked → select browser-agent-ext folder).
     3. Open the extension's options page and ensure "Enable pi bridge"
        is on and the URL points to ws://127.0.0.1:<port>.
     4. For WSL users: if Chrome on Windows cannot reach ws://127.0.0.1,
        set PI_BA_HOST=0.0.0.0 and point the extension at
        ws://<wsl-ip>:<port>.

   Retry by calling browser_agent_tools again once the above is fixed.
   ```

**`browser_agent_tools` schema:**

```ts
name: "browser_agent_tools",
label: "Browser Agent: Toolkit",
description:
  "Activates the browser-agent toolkit for this session. Call this FIRST, " +
  "before any other browser operation. It checks that the browser agent " +
  "(broker + Chrome extension bridge) is available and, if so, registers " +
  "the full toolkit (browser_run_task, browser_get_html, browser_get_console_logs, " +
  "browser_get_network, browser_evaluate_js, browser_run_js, and ~15 more) " +
  "so you can use them. If the agent is not available, returns a concise " +
  "error with instructions for the user. Safe to call multiple times — " +
  "subsequent calls are idempotent.",
promptSnippet:
  "Activate the browser agent toolkit to inspect or automate a browser — " +
  "call this before any other browser_* tool",
parameters: Type.Object({
  force_refresh: Type.Optional(Type.Boolean({
    description: "Re-probe connectivity even if tools were already registered",
    default: false,
  })),
}),
```

**Connectivity probe implementation:**
- Use `ws` package (broker is already ws-server; probe opens a client
  socket).
- Race against `setTimeout(800)` for initial connect; another 800 ms
  for the `welcome` frame.
- The probe sends `{v:1,kind:"probe"}` — a broker-only no-op request
  that returns current bridge status:
  `{ bridge_connected: boolean, bridge_version?: string, capabilities?: string[] }`.
- Close the probe socket after the response.
- Three distinct "unavailable" states:
  - **Broker unreachable** → "pi-browser-agent broker is not
    listening on ws://…"
  - **Broker up, bridge not connected** → "the Chrome extension is
    not connected — load/reload browser-agent-ext."
  - **Broker + bridge up, capability missing** → "extension version
    too old; upgrade browser-agent-ext."

**State management:**
- A module-level `registered: boolean` in `browser_agent_tools.ts`
  tracks whether `registerAllTools()` has already run. Reset on
  `session_start` so a reloaded session starts clean.
- `registerAllTools()` uses `pi.registerTool()` for each tool and
  sets `registered = true`. Not wrapped in `pi.setActiveTools()` —
  newly registered tools are active by default.
- If `force_refresh: true`, the probe is re-run, but we never
  *unregister* tools (pi doesn't expose a public un-register API);
  we simply re-probe and return the current status.

**Ordering guarantees** (per pi docs — confirmed):
- `pi.registerTool()` calls made during `execute()` are reflected in
  the **next** `pi.getAllTools()` and therefore in the next LLM
  prompt built by pi. From the LLM's perspective, after it receives
  the tool-result text from `browser_agent_tools`, the new tools
  are available on the next turn. This is the expected flow.

**Suggesting tool names in the result text.** The success payload
above **explicitly enumerates** the new tool names. Models that
pre-construct tool-call plans won't know about tools they've never
seen in their system prompt on the current turn, so the human-readable
list in the return value is the hint that lets them plan the next
turn correctly.

### General conventions for every tool

- Schemas use typebox (`import { Type } from "@sinclair/typebox"`) to
  match pi convention.
- Every tool that returns **text / html / json / logs**:
  - Accepts optional filters (`selector`, `levels`, `substring`,
    `limit`, `since`, etc.).
  - Description **must** say: *"Prefer using filters to return only
    what you need — if the result is large it is truncated and the
    full output is spilled to a temp file."*
  - Applies `truncateHead` or `truncateTail` from
    `@mariozechner/pi-coding-agent` (`DEFAULT_MAX_BYTES = 50KB`,
    `DEFAULT_MAX_LINES = 2000`). On truncation, write the full result
    to `os.tmpdir()/pi-browser-<tool>-<hexid>.{txt|json|html}` and
    append `"\n\n[Showing … of …. Full output: <path>]"` to the
    returned text.
- Screenshot output is always a compressed JPEG (max 1280px wide,
  quality 0.7) matching the `_compressScreenshot()` helper in
  `browser-agent-core/background/agent.js`. Large screenshots spill to
  a `.jpg` file and the tool returns the file path instead of the
  base64 blob. Threshold: 256 KB inline, spill otherwise.
- Every tool accepts an optional `tab_id` param. If omitted:
  - for `browser_run_task` and tools with `url` → uses the **agent
    tab** (dedicated, pinned, `chrome://newtab/` on first run).
  - other tools → last-used agent-tab; never the user's unrelated
    tab unless `use_active_tab: true` is passed.
- Every tool signals errors by throwing an `Error` (per pi's
  extension contract).

### 6.1 `browser_run_task`
- **Purpose:** run a natural-language browser task and return the
  final verdict + `task_id`.
- **Params:**
  ```ts
  {
    task: string;                           // required; natural-language
    url?: string;                           // optional start URL; if omitted, agent uses whatever's in the agent tab
    max_iterations?: number;                // default 20
    use_vision?: boolean;                   // default true
    tab_id?: number;                        // force a tab
    use_active_tab?: boolean;               // default false
  }
  ```
- **Behaviour:**
  1. Broker generates `task_id = uuidv4()`; creates
     `<state>/tasks/<task_id>.jsonl` with the initial header line.
  2. Sends `request { type:"run_task", params }` to the bridge.
  3. Bridge:
     - Ensures the agent tab is active (or uses `tab_id`).
     - Plugs a `debugLog` + `actionRecorder` into `AgentCore` that
       posts `event {topic:"task_step"}` frames to the broker.
     - Calls `agent.run(task)`; also forwards `onStatus` updates as
       `event {topic:"task_status"}` frames.
  4. Broker appends every event to the task jsonl file.
  5. On terminal state (`done`, `error`, `stopped`) the bridge sends a
     final `event {topic:"task_done"|"task_error"}` and a `response`
     with `{ task_id, status:"done"|"error"|"stopped", message }`.
  6. The pi tool calls `onUpdate?` on every event so the user sees
     live progress in the TUI, but the final return value is just
     `{ task_id, status, message, iterations }` + a short
     human-readable summary of the last 5 steps.
- **Cancellation:** `signal.aborted` → broker sends
  `cancelTask { task_id }` → bridge calls `agent.stop()` +
  `inputControl.abort()`.
- **Concurrency:** if another `run_task` is in-flight, respond
  `E_BUSY { current_task_id }`.

### 6.2 `browser_get_task_history`
- **Purpose:** return the recorded trace for a past or current task.
- **Params:**
  ```ts
  {
    task_id: string;                         // required
    format?: "jsonl" | "markdown" | "summary";   // default "markdown"
    last?: number;                           // return only the last N steps
    include_screenshots?: boolean;           // default false; inline base64 of each step's annotated screenshot
    filter?: { action?: string; url_contains?: string };
  }
  ```
- **Behaviour:** reads `<state>/tasks/<task_id>.jsonl`. **No bridge
  roundtrip.** Output is truncated per §6 conventions.

### 6.3 `browser_list_tasks`
- **Params:** `{ limit?: number /*default 50*/, status?: "done"|"error"|"stopped"|"running" }`
- Lists tasks recorded in `<state>/tasks/`, newest first.

### 6.4 `browser_cancel_task`
- **Params:** `{ task_id: string }`. Sends `cancelTask`.

### 6.5 `browser_get_screenshot`
- **Params:**
  ```ts
  {
    url?: string;                            // if present, navigate agent tab there first
    tab_id?: number;
    use_active_tab?: boolean;
    full_page?: boolean;                     // default false
    selector?: string;                       // if present, crop to this element
    wait_until?: "load" | "networkidle" | "settle";  // default "settle"
    format?: "jpeg" | "png";                 // default "jpeg"
    quality?: number;                        // jpeg only, default 0.7
    max_width?: number;                      // default 1280
  }
  ```
- **Returns:** `{ data_base64?, mime, width, height, url, title, path? }`.
  If size > 256 KB, omit `data_base64` and set `path`.
- **Implementation:** `Page.captureScreenshot { captureBeyondViewport: full_page }`
  or `chrome.tabs.captureVisibleTab` for viewport-only path when the
  debugger isn't attached.

### 6.6 `browser_get_html`
- **Params:**
  ```ts
  {
    url?: string;
    tab_id?: number;
    use_active_tab?: boolean;
    selector?: string;                       // "prefer selector to return just what you need"
    selector_all?: boolean;                  // if true, return concatenation of all matches
    rendered?: boolean;                      // default true — post-JS HTML from the tab
    wait_until?: "load"|"networkidle"|"settle";
    strip?: ("script"|"style"|"comments")[]; // remove these before returning
    max_bytes?: number;                      // default 50 000
  }
  ```
- **Description must include:** *"Prefer a CSS `selector` to return
  only the subtree you need. Large pages are truncated — full HTML is
  written to a temp file."*

### 6.7 `browser_get_dom_info`
- **Purpose:** detailed info about a single or many elements
  (attributes, rect, styles, visibility, textContent, listeners).
- **Params:**
  ```ts
  {
    url?: string;
    selector: string;                        // required
    selector_all?: boolean;                  // default false; if true, limit to `limit`
    limit?: number;                          // default 20
    include?: ("attributes"|"rect"|"textContent"|"innerHTML"|
               "accessibility"|"visibility"|"event_listeners"|
               "outer_html")[];              // default all except "innerHTML"/"outer_html"
  }
  ```
- **Implementation:** content-script primitive (reuse pieces of
  `browser-agent-core/content/extractor.js` element-info code) or
  `DOMDebugger.getEventListeners` via CDP for the listener bit.

### 6.8 `browser_get_computed_styles`
- **Params:**
  ```ts
  {
    url?: string;
    selector: string;                        // required
    properties?: string[];                   // "prefer to list only the properties you need"
    pseudo?: string;                         // "::before" | "::after" | "::marker" | "hover" | "active" | …
    include_matched_rules?: boolean;         // default true — which selector won the cascade
    include_inherited?: boolean;             // default false
    include_box_model?: boolean;             // default true — offset/padding/border/margin boxes
  }
  ```
- **Implementation:** CDP `CSS.enable`, `DOM.getDocument`, resolve
  node via `DOM.querySelector`, then `CSS.getComputedStyleForNode`
  and `CSS.getMatchedStylesForNode`. Property filter applied on the
  returned map.

### 6.9 `browser_get_console_logs`
- **Params:**
  ```ts
  {
    url?: string;                            // if present, navigate first (after buffer has been armed)
    tab_id?: number;
    use_active_tab?: boolean;
    levels?: ("log"|"info"|"warn"|"error"|"debug")[];
    substring?: string;                      // "prefer a filter to return only relevant logs"
    regex?: string;
    since?: number;                          // epoch ms
    last?: number;                           // keep only last N after filters
    include_exceptions?: boolean;            // default true (unhandled errors)
    include_stack?: boolean;                 // default true
  }
  ```
- **Buffer:** per-tab CDP `Runtime.enable` + `Log.enable` +
  `Console.enable`, ring buffer of **2000** entries. Buffer is armed
  when the tab is first touched by any browser tool, or on SW startup
  for every existing tab. Survives SW restart via
  `chrome.storage.local['piBridge.consoleBuf.<tabId>']` with a soft
  cap of 512 KB — when exceeded, oldest half is dropped.
- Description must encourage filtering.

### 6.10 `browser_get_network`
- **Params:**
  ```ts
  {
    url?: string;
    tab_id?: number;
    use_active_tab?: boolean;
    filter?: {
      method?: string | string[];           // "GET" / ["GET","POST"]
      status?: number | number[];
      status_gte?: number;                  // >= X
      status_lt?: number;                   // < X
      type?: ("xhr"|"fetch"|"document"|"script"|"stylesheet"|
              "image"|"font"|"websocket"|"manifest"|"other")[];
      url_contains?: string;
      url_matches?: string;                 // regex
      mime_contains?: string;
      failed_only?: boolean;                // status==0 or >=400
      since?: number;
      until?: number;
      duration_gte_ms?: number;
      last?: number;
      initiator_contains?: string;
    };
    include_request_headers?: boolean;       // default false
    include_response_headers?: boolean;      // default false
    include_request_body?: boolean;          // default false; size-capped
    include_response_body?: boolean;         // default false; size-capped
    body_max_bytes?: number;                 // default 64 * 1024 per entry
    include_timing?: boolean;                // default true
  }
  ```
- **Buffer:** per-tab CDP `Network.enable`, ring buffer of **500**
  entries keyed by `requestId`, with lazy response-body fetch via
  `Network.getResponseBody` only when `include_response_body` is true.
- **Description must include:** *"Always pass filters (status, url
  substring, type, failed_only, since) — unfiltered logs are
  truncated and spilled to a temp file. Use `include_*_body` only when
  you actually need to inspect payloads; bodies are size-capped."*
- **Returns:** `{ entries: [...], total, truncated, full_output_path? }`.

### 6.14 `browser_run_js`
- **Purpose:** run a longer JS program (possibly multiple statements,
  possibly with imports via dynamic `import()`) in the page context and
  return its result and/or console output produced during execution.
- **Params:**
  ```ts
  {
    url?: string;
    tab_id?: number;
    use_active_tab?: boolean;
    code: string;                            // required, full function body; wrapped in async IIFE automatically
    args?: unknown[];                        // serialised and passed as function arguments
    return_by_value?: boolean;               // default true
    world?: "main" | "isolated";             // default "main"
    timeout_ms?: number;                     // default 30000
    capture_console?: boolean;               // default true — capture console.* during the run
  }
  ```
- **Implementation:**
  1. Wrap `code` as `(async function(...args){ ${code} }).apply(null, ${JSON.stringify(args)})`.
  2. If `capture_console`, temporarily patch `console.{log,info,warn,error,debug}`
     inside the expression to also push onto a `__pi_log` array, restore
     after; read `__pi_log` back via `Runtime.evaluate`.
  3. `Runtime.evaluate { awaitPromise: true, returnByValue }`.
  4. On timeout, abort the call (no CDP abort primitive — we fall back
     to a `Runtime.releaseObjectGroup` + unattach/reattach for cleanup).
- **Returns:** `{ value, console_entries, exception?, duration_ms }`.
- Same truncation convention; `code` and `console_entries` go through
  the temp-file spill.

## 7. Service-worker lifecycle — the hard parts

MV3 kills the SW after ~30 s idle. Handling:

1. **Alarms-based keep-alive**: on bridge start we register
   `chrome.alarms.create('pi-bridge-ka', { periodInMinutes: 0.4 })`.
   The handler pokes the socket. Alarms reliably wake the SW.
2. **Message traffic** already restarts the idle timer, so during a
   running task the SW stays hot without the alarm.
3. **State persistence** (`chrome.storage.local`):
   - `piBridge.currentTask` — task_id, started_at, tab_id, iter.
   - `piBridge.consoleBuf.<tabId>` — ring buffer of console entries
     (flushed every N messages or 1 s, whichever first).
   - `piBridge.networkBuf.<tabId>` — similarly for network entries.
     Bodies are **not** persisted; only metadata.
4. **Reconnect protocol**: on every ws open we send
   `hello { extensionId, version, capabilities, resumingTaskId? }`.
   If broker has a task in a non-terminal state for this extension it
   replies with `welcome { resumeTaskId }` so the bridge can resume
   pushing events. (The actual `AgentCore` run is SW-local; if the SW
   was killed mid-run, the task is marked `interrupted` and the pi
   tool gets `E_BRIDGE_DISCONNECTED`.)
5. **Flush-on-suspend**: `chrome.runtime.onSuspend` fires before
   termination. We flush all in-memory buffers to storage and tear
   down the debugger cleanly.
6. **Debugger-attach survival**: `chrome.debugger` sessions die when
   the SW dies. On SW wake we look at stored state and re-arm
   buffers (`Network.enable`, `Log.enable`, etc.) on all tabs.

## 8. CDP single-attach refactor (prerequisite)

Chrome allows **one** `chrome.debugger` client per tab. The existing
CDP input-control backend in
`browser-agent-ext/lib/browser-agent-input-control` currently attaches
directly. Adding console + network listeners from a different code path
would race.

**Action:**
- Create `lib/pi-browser-agent-bridge/src/cdp-inspector.js` as the
  single owner of attach/detach. Interface:
  ```js
  class CdpInspector {
    async acquire(tabId): Promise<CdpLease>   // refcounted
    async release(lease): void
    async send(tabId, method, params?): Promise<any>
    on(tabId, event, handler): off()
  }
  ```
- Refactor `CdpInputControlBridge` (in
  `browser-agent-input-control/src/debugger-transport.js`) to accept
  an optional `inspector` and, when present, route
  attach/send/subscribe through it. Existing API stays the same; if
  `inspector` is not passed it continues to own attach/detach the old
  way (keeps the extension runnable without the bridge loaded).
- This is step 1 of rollout; every other handler depends on it.

## 9. Concurrency & locking

- `AgentCore` runs are **serial**. A second `run_task` returns
  `E_BUSY { current_task_id }`.
- Inspection tools on a non-agent tab run in parallel with a running
  task — they only attach a second CDP *subscription* (not attach) via
  the shared inspector.
- Per-tab lock for navigation-ish tools (`navigate`, `reload`,
  `wait_for`, `clear_site_data`, `get_screenshot(full_page)`).
  `dispatcher.js` enforces this via a `Map<tabId, Promise>` chain.
- Broker accepts **one** bridge client at a time. If a second
  connection arrives, the older one is closed (stale SW leftover from
  a reloaded extension).

## 10. Agent-tab policy

- First time the bridge needs a tab and none is marked as agent tab,
  it opens `chrome.tabs.create({ url: 'chrome://newtab/', pinned: true, active: false })`
  and stores `piBridge.agentTabId = tab.id`.
- The tab is re-discovered across SW restarts by id; if the stored id
  is gone, a new one is created.
- Tool param `use_active_tab: true` overrides and uses the currently
  focused tab. Default stays safe.
- `browser_run_task` activates the agent tab (brings to front) at
  start and optionally navigates to `url`.

## 11. Long-result handling (pi convention)

pi does **not** auto-truncate tool results — each tool must. Pattern
(taken from pi's built-in `bash` / `find` tools):

```ts
import {
  truncateHead, truncateTail, formatSize,
  DEFAULT_MAX_BYTES, DEFAULT_MAX_LINES,
} from "@mariozechner/pi-coding-agent";
import { tmpdir } from "node:os";
import { randomBytes } from "node:crypto";
import { join } from "node:path";
import { writeFile } from "node:fs/promises";

async function spillAndTruncate(text: string, ext = "txt") {
  const t = truncateHead(text, { maxLines: DEFAULT_MAX_LINES, maxBytes: DEFAULT_MAX_BYTES });
  if (!t.truncated) return { text: t.content, truncation: undefined, fullOutputPath: undefined };
  const path = join(tmpdir(), `pi-browser-${randomBytes(8).toString("hex")}.${ext}`);
  await writeFile(path, text, "utf8");
  return {
    text:
      t.content +
      `\n\n[Showing ${t.outputLines} of ${t.totalLines} lines (${formatSize(DEFAULT_MAX_BYTES)} limit). ` +
      `Full output: ${path}]`,
    truncation: t,
    fullOutputPath: path,
  };
}
```

All text-returning tools use this. The tool's returned `details` field
must include `{ truncation, fullOutputPath }` so pi's UI can surface the
warning.

For JSON-heavy tools (`browser_get_network`,
`browser_get_computed_styles`, etc.) stringify with
`JSON.stringify(result, null, 2)` and apply the same pattern with
`ext: "json"`.

Every tool's description must include a sentence like:

> *"Prefer filters/selectors to narrow the result. If the output is
> large, it is truncated and the full result is written to a temp
> file whose path is included in the response."*


## 14. Security posture

- Broker binds `127.0.0.1` by default; no network exposure.
- No token (locked answer #4). This is explicitly fine because:
  - Any local process with this port can already attach a debugger
    to Chrome directly.
  - User must install both sides deliberately.
- `evaluate_js` / `run_js` / `clear_site_data` / `navigate` are free
  (locked answer #6). The extension is the trust boundary; if the
  user installs it they accept the power.
- Tools log method names to pi's tool-call transcript (which the user
  sees), never log request/response bodies or cookies unless the
  caller explicitly asked for bodies.

## 17. Caveats & gotchas the implementer must respect

1. **`AGENTS.md` rule**: no synthetic DOM input. All user-input
   actions go through `python-input-control` / `CdpInputControlBridge`.
   `evaluate_js` and `run_js` **read/compute only** from the LLM's
   perspective — they are not allowed to be used to simulate clicks or
   typing inside the agent loop. The tools themselves don't enforce
   this (they're free-form), but the `run_task` prompt must not
   encourage the agent to bypass the executor via js.
2. **Only one `chrome.debugger` client per tab** → the shared
   inspector in §8 is mandatory.
3. **Service-worker gets killed** → `alarms` permission + persistent
   buffers + reconnect-on-wake (§7).
4. **Buffer arming timing**: `Network.enable` must be called **before**
   navigation to catch the first request. On SW wake, arm buffers on
   all existing tabs before processing any tool request.
5. **JPEG compression identical to `_compressScreenshot()`** in
   `browser-agent-core/background/agent.js` (max 1280 wide, quality
   0.7, OffscreenCanvas).
6. **Big results always spill to a temp file** and return the path —
   never inline > 50 KB text or > 256 KB screenshot.
7. **Filters are optional but the tool description must encourage
   them.** Explicitly say: *"Prefer passing filters/selectors — the
   result is truncated and the full data is spilled to a temp file if
   large."* in every text/network/log/dom tool's `description`.
8. **Agent tab** must be pinned and titled so the user can easily spot
   it and not close it by accident.
9. **Windows path separators** in temp-file paths — use `path.join`,
   never string-concat.
10. **WSL loopback** may not work on every user's config. Broker
    README must describe the fallback: set `PI_BA_HOST=0.0.0.0`, point
    the extension at `ws://<wsl ip>:7878`.
11. **CDP `Runtime.evaluate` timeouts** aren't a CDP primitive — we
    race a `setTimeout(timeout_ms)` and, on firing, detach+reattach
    the tab session (costly but correct). Document this in
    `browser_run_js`.
12. **Extension reload** (↺ in `chrome://extensions`) → ws drops →
    any in-flight pi tool gets `E_BRIDGE_DISCONNECTED`. Tool retries
    are the caller's responsibility.
13. **Extension ID hasn't been fixed** in the manifest, so reloading
    may change it and break the native-messaging host allow-list.
    Irrelevant to this feature (the broker doesn't care), but worth
    noting in the README.
14. **Broker port collision**: if `7878` is busy, fail fast with a
    clear "port busy — set PI_BA_PORT" message rather than picking a
    random port (the extension would then not know where to connect).
