## 2. Things I'd push back on / clarify before coding

These are worth deciding up front because they affect the structure of
both the lib and the docs.

### 2.1 "Same protocol" means *semantic protocol*, not *native-messaging framing*

The protocol as it exists today is actually two things stacked:

| Layer | What | Bound to |
|---|---|---|
| **Semantic** | `{id, command, params, context}` ⇢ `{id, status, error}` | Stable — describes *what* is happening |
| **Transport** | 4-byte little-endian length + UTF-8 JSON (Chrome native messaging framing) | Stable only for the python host; it's an artefact of `chrome.runtime.connectNative` |

The in-extension lib runs *inside the service worker's JS realm*. It does **not
need length-prefixed framing** — there is no byte stream, just a function
call. Forcing it to speak native-messaging framing would be pure theatre.

**Recommendation:** the docs define the semantic layer as canonical, and
transport as a pluggable concern. We document three transports:
- Native messaging (how `python-input-control` is wired)
- In-process (how `browser-agent-input-control` is wired — direct method call,
  protocol envelope still honoured on the API surface)
- Optional future: WebSocket / HTTP (for remote hosts)

This is a much cleaner story than "re-implement stdio framing in JavaScript
for no reason".

### 2.2 `BrowserContext` is partly meaningless for the CDP backend

The `context` object today carries:

```
screenX, screenY, outerHeight, innerHeight, outerWidth, innerWidth,
devicePixelRatio, scrollX, scrollY
```

Everything in there exists so the **OS-level** backend can translate a viewport
coordinate into a physical-screen pixel and pass the desktop-bounds check. The
CDP backend doesn't do any of that — `Input.dispatchMouseEvent` uses viewport
CSS pixels directly. So `context` becomes **advisory** for CDP.

**Recommendation:** keep the field in the protocol for compatibility, but
document it as "MAY be used by OS-mapping backends, MUST be ignored by pure
viewport backends (CDP, headless)". Both backends still accept the exact same
request shape, which is what we want for the extension's swap logic.

### 2.3 `tabId` isn't in the protocol — it needs to be

`python-input-control` targets "whatever the OS focus is"; it has no tab
concept. The CDP backend targets a specific tab via `chrome.debugger.attach`.

**Recommendation:** don't put `tabId` in the protocol. Keep the protocol
browser-agnostic. Instead, the JS `CdpInputControlBridge` gets a reference to
the existing `BrowserBridge` in its constructor and calls
`bridge.getActiveTabId()` before each execute. This mirrors what the OS
backend does implicitly (it acts on the focused window).

### 2.4 User-visible side-effects of `chrome.debugger`

- Chrome shows a yellow **"`<extension>` started debugging this browser"**
  banner for as long as we are attached. This is non-dismissable and is part
  of the security model. We should call this out in the UI when the user picks
  this backend (a one-line note next to the radio button).
- Only **one debugger client per tab**. If the user has DevTools open on the
  target tab, `attach` fails. We need a clear error, not a silent hang.
- Some sites sniff for debugger attachment via timing / fingerprinting. Lower
  stealth than OS-level input. Worth documenting.

### 2.5 Folder naming nit — RESOLVED

Renamed to **`input-control-protocol`** (singular). The current empty
`browser-agent-ext/lib/inputs-control-protocol/` directory will be removed in
favour of the new submodule path.

### 2.6 "Expose all the same functionality"

All existing commands map cleanly to CDP:

| Command | CDP primitive |
|---|---|
| `mouse_move` | `Input.dispatchMouseEvent {type: mouseMoved}` (looped along a Bézier path) |
| `mouse_click` | `mouseMoved` + `mousePressed` + `mouseReleased`, `clickCount` for doubles |
| `scroll` | `Input.dispatchMouseEvent {type: mouseWheel, deltaX, deltaY}` (stepped for smoothness) |
| `type` | Per-char `Input.dispatchKeyEvent {keyDown}` + `{keyUp}` with WPM-paced `setTimeout` (we avoid `Input.insertText` because it doesn't fire real keydown events — many pages won't react) |
| `press_key` | `keyDown` + `keyUp` with mapped `key`/`code`/`windowsVirtualKeyCode` |
| `press_shortcut` | `keyDown` modifiers (with `modifiers` bitmask) + key, then reverse |
| `pause` | `await sleep(ms)` (cancellable) |
| `sequence` | iterate children |
| `cancel` | trip internal `AbortSignal`, detach debugger |

Human-like behaviour (Bézier paths, WPM, jitter, extra-pause-after-punctuation)
ports straight from `python-input-control/src/python_input_control/{mouse_motion,timing,randomness,backends/pynput_keyboard}.py`.

### 3.1 Public API — must be a drop-in for `InputControlBridge`

```js
// In browser-agent-input-control
import { CdpInputControlBridge } from 'browser-agent-input-control';

const cdp = new CdpInputControlBridge({ bridge /* BrowserBridge instance */ });
await cdp.execute('mouse_click', { x: 120, y: 240, button: 'left' }, ctx);
cdp.abort();        // same semantics as InputControlBridge.abort()
cdp.disconnect();   // detach debugger
```

Signature, return value and error contract **must match** the existing
`InputControlBridge` (`input-control.js`). That way `ActionExecutor` in core
needs zero changes.

Shared error shape:

| python bridge | CDP bridge |
|---|---|
| `InputControlError` | `InputControlError` (re-export same class, or have compatible `name`/`message`) |
| `InputControlTimeoutError` | same |
| `name: 'InputControlAbortError'` on abort | same (agent.js checks for exactly this name) |

### 3.2 Dispatcher internals

Shape follows the python dispatcher, minus framing:

```js
class Dispatcher {
  async handle({ id, command, params, context }, signal) {
    try {
      const cmd = parseCommand(command, params, context); // validation
      await this.route(cmd, signal);
      return { id, status: 'ok' };
    } catch (err) {
      if (err.name === 'CommandCancelledError') return { id, status: 'error', error: 'Command cancelled' };
      return { id, status: 'error', error: err.message };
    }
  }
}
```

The bridge's `execute()` builds the envelope, calls `dispatcher.handle(...)`,
and resolves/rejects accordingly — so consumers see the same
`{status:'ok'|'error'}` envelope the python host sends.

### 3.3 Cancellation

- `CdpInputControlBridge` owns one `AbortController` per in-flight execute.
- Every `await sleep(ms)` goes through a `cancellableSleep(ms, signal)` helper
  that rejects with `CommandCancelledError` when the signal aborts.
- `bridge.abort()` → trips the controller → all sleeps unwind → detach debugger.
- Exactly matches the python `cancel_event` story, just re-spelled in JS.

### 3.4 Debugger transport

```js
class DebuggerTransport {
  async ensureAttached(tabId) { /* attach if not already */ }
  async send(method, params)  { /* chrome.debugger.sendCommand */ }
  async detach()              { /* chrome.debugger.detach */ }
}
```

Handles:
- Attach on first command, reuse across commands in the same run
- One shared transport per tab per bridge instance
- On `detach()` → clears attached-tabs cache
- `chrome.debugger.onDetach` listener → if the user closes DevTools / reloads /
  closes the tab, we clear the attached state and surface an error on the next
  command

### 3.5 Human-like motion (port of python)

- `buildBezierPath(start, end, rng)` → array of {x, y, t}.
- `estimateMouseDurationMs(distance)` — uses the same Fitts-ish formula as
  python.
- Steps dispatched with `setTimeout` so the signal can cancel mid-movement.
- For typing: `wpmToInterKeyDelayMs`, `jitteredDelayMs`, `extraPauseAfterChar`
  — straight port.

### 3.6 Key map (CDP specifics)

CDP `Input.dispatchKeyEvent` wants:
- `type`: `keyDown` / `keyUp` / `rawKeyDown` / `char`
- `key`: DOM `KeyboardEvent.key` value (e.g. `"a"`, `"Enter"`, `"ArrowLeft"`)
- `code`: DOM `KeyboardEvent.code` value (e.g. `"KeyA"`, `"Enter"`)
- `windowsVirtualKeyCode`: old-school VK code (crucial for some form
  validators)
- `text`: the printable character for printables (this makes the key event
  actually insert a character)
- `modifiers`: bitmask `alt=1, ctrl=2, meta=4, shift=8`

We build one table keyed by normalised logical names (the same aliases python
uses — `esc`→`escape`, `ctrl`→`control`, `cmd`→`command`, etc.) and emit the
right values.

Shift handling for shifted symbols mirrors python: build a `{ '!': '1', ... }`
map and flip the `shift` modifier + generate the correct `text`.

### 3.7 Core framework: zero changes required, but one clarification

`browser-agent-core` only relies on duck typing. It just wants
`this._inputControl.execute(command, params, context)`. So we don't edit
`browser-agent-core` at all. That's a feature — a separate repo with zero
coupling.

I'd add a short note in `browser-agent-core/README.md` clarifying that the
`InputControlBridge` is one of *several* interchangeable implementations — but
that's optional and non-blocking.

### 3.8 Wiring in `browser-agent-ext/background/sw.js`

```js
import { InputControlBridge }    from '../lib/browser-agent-core/background/index.js';
import { CdpInputControlBridge } from '../lib/browser-agent-input-control/index.js';

const DEFAULT_INPUT_BACKEND = 'cdp';   // ← CDP is default for new installs

function createInputControl({ inputBackend, bridge }) {
  const backend = inputBackend || DEFAULT_INPUT_BACKEND;
  switch (backend) {
    case 'native': return new InputControlBridge();             // python-input-control
    case 'cdp':
    default:       return new CdpInputControlBridge({ bridge });
  }
}
```

Picked from `chrome.storage.local.get('inputBackend')` in the `start_task`
handler, alongside the existing `provider`, `apiKey`, etc. If the key is
absent (fresh install / upgrade from before this feature), the default `'cdp'`
is applied **and persisted** so the Settings UI reflects it.

`stop_task` handler already calls `currentInputControl.abort()`; it keeps
working because both bridges honour the same `abort()` contract.

## 4. Protocol docs — what goes in `inputs-control-protocol`

Target reader: someone implementing a third backend (say, Rust + enigo, or
Node.js + robotjs, or a remote agent).

### 4.1 `README.md`

- One-paragraph overview: what this protocol is, what it isn't.
- List of canonical implementations (`python-input-control`,
  `browser-agent-input-control`).
- Versioning policy (semver on the message shapes).
- Table of contents for the other docs.

### 4.2 `PROTOCOL.md` — the ground truth

- Envelope schema (command + response).
- Required vs optional fields, with a precise JSON Schema block.
- Rules for `id` (non-empty string, echoed in the response).
- Rules for `params` (object), `context` (object), `command` (enum).
- Exactly one action per request; batching is via `sequence`.

### 4.3 `COMMANDS.md`

One section per command. For each:
- JSON Schema for `params`.
- Behavioural contract (e.g. *"MUST pause between press and release by at
  least 10 ms"*, *"SHOULD pace typing according to `wpm`"*).
- Error cases a compliant implementation MUST surface.
- Three worked examples (request + expected response).

Commands documented:
- `mouse_move`, `mouse_click`, `scroll`
- `type`, `press_key`, `press_shortcut`
- `pause`
- `sequence`
- `cancel`

### 4.4 `CONTEXT.md`

- Fields in the `BrowserContext` object.
- **Which fields each class of backend uses** (OS-screen-mapping vs
  viewport-native). This is the single place where we make it clear that CDP
  backends MAY ignore geometry fields.
- How to compute them from a web page (sample JS snippet).

### 4.5 `ERRORS.md`

- Envelope: `{id, status: "error", error: "message"}`.
- Standard error messages (validation, unknown command, cancelled, out of
  bounds, backend unavailable).
- Guidance on surfacing vs retrying.

### 4.6 `TRANSPORTS.md`

- **Native messaging** (Chrome): 4-byte LE length + UTF-8 JSON payload, max
  4 MiB. Reference `python-input-control/protocol.py`.
- **In-process**: direct async function call on a `Bridge`-like object.
  Reference `browser-agent-input-control`.
- **WebSocket / TCP (informative, no v1 implementation)** — locked decision
  §0. Document the recommended framing only, so a third party can build it
  later: one JSON message per WS text frame, max 4 MiB, ping every 30 s, EOF
  / close = cancel any in-flight command. Explicitly mark this section as
  *informative* (not normative for v1).
- Cancellation semantics per transport (EOF-on-stdin = cancel for native
  messaging; `AbortController` for in-process; close-frame for WS).

### 4.7 `BACKENDS.md`

Implementer guidance:
- OS-input (pyautogui/pynput/enigo/robotjs): translate viewport→screen using
  context fields, do desktop-bounds check.
- CDP: ignore geometry, dispatch via `Input.dispatch*Event`.
- Headless/test: record calls, return `ok` immediately.
- Rate-limiting and jitter expectations (so automation looks human).

### 4.8 `CHANGELOG.md`

Start with `v1.0.0` — the current shape frozen as-is.

### 4.9 `examples/`

A dozen `request.json` + `response.json` pairs covering happy paths and
error paths. Makes it trivial to copy-paste into unit tests in any language.

## 5. Test strategy

### 5.1 `browser-agent-input-control` unit tests (Jest)

- **Dispatcher validation**: same cases as
  `python-input-control/tests/test_dispatch.py` — unknown command, missing
  fields, bad types.
- **Fake CDP transport**: record the sequence of `(method, params)` calls.
  Then assert e.g. `type("hi")` produces exactly `[keyDown h, keyUp h, keyDown i, keyUp i]`
  with inter-key delays in the expected WPM range.
- **Cancellation**: start a long `type`, call `abort()` after 50 ms, assert
  the promise rejects with `InputControlAbortError` and no further CDP calls
  are made.
- **Key map**: every python alias resolves; shifted symbols set shift modifier;
  `Enter`/`Tab`/`Escape` carry both `key` and `code`.
- **Mouse motion**: path has ≥ N points for distance ≥ D, first point ≈ current
  position, last point = target, no NaN.

### 5.2 Extension smoke test (manual)

Script in `browser-agent-ext/README.md`:
1. Pick a known test site (e.g. `the-internet.herokuapp.com/login`).
2. Run the same task with `inputBackend=native`, confirm success.
3. Switch to `inputBackend=cdp`, confirm success (and yellow debug banner).
4. Run a task, hit **Stop** mid-typing, confirm it aborts within 200 ms and
   re-enables the Run button.

### 5.3 No regressions in `browser-agent-core`

Run existing `browser-agent-core/tests` — should pass untouched because core
isn't modified.
